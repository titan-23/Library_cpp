# ビームサーチ・ライブラリの高速化案

## 対象

- `beam_search.cpp`
- `beam_search_turn.cpp`
- `candidates.cpp`
- `hash_dict.cpp`

問題固有の `State`、単純版、compose版、radix版は対象外とする。

## 優先順位

1. 候補のハッシュ表を、Wに比例する大きさへ制限する。
2. 脱落済み候補を、並べ替えより前に除去する。
3. `Action` は候補への採用が決まってから保存する。
4. 親番号による並べ替えを、配列への振り分けに置き換える。
5. `Action` の保管場所を固定長ブロック方式にする。
6. 木や候補の構造体を小さくする。
7. 固定ビーム幅では時刻計測と統計処理を外す。

## 挙動への影響

| 改善 | 探索結果への影響 |
|---|---|
| 古い値を位置指定で無効化し、定期的に表を作り直す | 変わらない。値 `-1` と同じ規則を保つ |
| ハッシュ表の容量変更、再度混ぜる処理の省略 | 変わらない。格納位置だけが変わる |
| 全ターン重複排除用の表を分離する | 現在の `-2` と周期初期化の規則を再現すれば変わらない |
| 脱落済み候補の早期除去 | その時点の生存候補集合は変わらない。同点順が変わると、後の探索結果は変わりうる |
| `Action` の保存を採用後へ遅らせる | 変わらない。ただし `Action` は通常の値型であることを前提とする |
| 次世代の最終位置へ `Action` を直接保存する | 変わらない。構築・破棄の時期だけ変わる |
| 親番号による配列振り分け | 同点順まで再現すれば変わらない。再現しなければ後の探索結果は変わりうる |
| 良い候補から先に展開する | 変わりうる。乱数の消費順と同点候補の採否も変わるため、任意機能にする |
| 固定長ブロック方式の `Action` 保管 | 変わらない。`Action` を参照経由で変更しないことが前提 |
| 構造体と `ActionId` の縮小 | 値が収まり、ビット詰めが正しければ変わらない |
| セグメント木の初期化範囲削減 | 未使用の葉を正しく初期化すれば変わらない |
| 固定幅専用経路 | 幅調整と統計が無効な場合に限れば変わらない |

挙動を完全に維持したい場合は、候補へ列挙順番号を付け、比較を `(親番号, スコア, 列挙順番号)` にする。脱落候補を先に除去しても、生存する同点候補の順序を固定できる。

ただし、現在の `std::sort` は同点要素の順序を保証しない。現在の候補順まで完全に固定するには、現行側にも列挙順番号を追加して比較規則を明文化する必要がある。

## 1. 候補のハッシュ表

現在は最悪候補を追い出しても、古いハッシュ値を値 `-1` として表に残している。このため表の要素数が一時採用された候補数まで増え、再構築と初期化が重くなる。

単純な削除機能の追加は第一候補ではない。開番地法では、削除済み印の管理や後続要素の移動が必要になり、削除自体にも費用がかかる。

推奨案は「位置指定での無効化と、定期的な一括再構築」である。

- 各候補にハッシュ表内の位置を保存する。
- 追い出すときは、ハッシュ値を再探索せず、その位置の値を直接 `-1` にする。
- 表の容量は約4Wに固定する。
- 使用済み位置が約2Wまで増えたら、生存中のW件だけで表を作り直す。
- 現在の候補を管理する表と、全ターンをまたぐ重複排除用の表を分ける。
- `State` が十分拡散されたハッシュ値を返す場合は、`HashDict` 内で再度ハッシュを混ぜない。

現状の `func.set(old_hash, -1)` も古いハッシュ値を再探索している。位置指定の無効化なら、この探索を1回減らせる。一括再構築はW回程度の置換につき1回、W件を連続して入れ直す処理なので、置換1回当たりでは定数時間になる。

この方式は、置換が少ないときは再構築が発生せず、置換が多いときも表の大きさをWに比例する範囲へ抑えられる。現在の `HashDict` の連続領域と16要素同時比較も維持できるため、削除機能を追加するより定数倍が良いと見込む。

`Candidates::reset` の `func.inner_len() == 1` は、初期容量が16なので成立しない。また `HashDict(8W)` は内部で約16W以上を確保するため過剰である。

## 2. 脱落済み候補を早く捨てる

可変ターン版は、一度採用された候補をすべて `new_candidates` に追加する。後から追い出されても、並べ替えと木の更新まで残る。

候補列挙後、並べ替え前に除去する。

```cpp
int dst = 0;
for (auto &c : new_candidates) {
    if (is_survived_node[c.aid]) {
        new_candidates[dst++] = c;
    } else {
        arena_release(c.aid);
    }
}
new_candidates.resize(dst);
```

さらに進めるなら、各候補集合の最終的な生存候補だけを列挙後に集める。一時的に採用されただけの候補は、最初から `new_candidates` に入れない。

## 3. Actionの保存を遅らせる

通常版は既存の `push_lazy` を使わず、`Action` を値渡ししている。枝刈り基準値やハッシュ重複で落ちる候補にも、コピーが発生する可能性がある。

処理を次の2段階に分ける。

1. スコア、ハッシュ値、親番号だけで採否と格納位置を決める。
2. 採用された場合だけ、その位置へ `Action` を保存する。

可変ターン版も、`arena_put_reserve()` を候補採用後へ移す。落ちる候補に対する空き番号の取得と返却をなくせる。

## 4. Actionの二重保存をなくす

通常版は `Action` を一度 `candidates.next_beam` に保存し、`finalize_generation` で `gblock` へ移動している。

次世代の保管領域を先にW件分用意し、候補の格納位置と `Action` の格納位置を一致させる。採用時に最終位置へ直接保存すれば、世代確定時はスコアや親番号だけを整理すればよい。

スコア、ハッシュ値、親番号、`ActionId` と、`Action` 本体は別々に保管する。候補管理中に大きな `Action` を読み込まないようにする。

## 5. 並べ替えを減らす

`parent_leaf` と `par` は、0から始まる密な整数である。全候補を比較で並べ替える必要はない。

1. 親ごとの候補数を数える。
2. 累積和で各親の書き込み位置を決める。
3. 候補を親ごとの区間へ振り分ける。
4. 同じ親の区間だけスコア順にする。

同じ親の候補が少ない場合は、汎用の `std::sort` より次が軽い。

- 2件：1回の比較交換
- 少数：挿入ソート
- 多数：`std::sort`

通常版はスコア昇順に並べた後、後ろから展開しているため、同じ親では悪い候補から展開している。完全な再現性が不要なら、良い候補から展開して枝刈り基準値を早く下げる。

## 6. Actionの保管場所

可変ターン版は、`action_pool` の再確保で参照が無効になるため、展開する葉の `Action` をコピーしている。

`Action` を移動しない固定長ブロックへ保存する。

- ブロック長は2の冪にする。
- `ActionId` にブロック番号とブロック内位置を詰める。
- 空いた `ActionId` は一覧で再利用する。

これにより、`Action` を参照したまま `apply_op`、候補列挙、`rollback` を行える。

## 7. 構造体を小さくする

- `TreeNode` の種類を `aid` の上位ビットへ詰め、16バイトから12バイトへ縮める。
- `ActionId` は、最大ターン数と最大幅が収まる場合は64ビットから32ビットへ縮める。
- `record_history=false` では履歴用の `node_id` を構造体から完全に除く。
- セグメント木の `pair<ScoreType,int>` は、余白が出ない専用構造体にする。
- `Candidates::reset` ではセグメント木全体を初期化せず、未使用の葉だけを初期化する。

## 8. 固定ビーム幅専用の経路

`is_adjusting=false` でも、各ターンで時刻計測、平均更新、`width_hist` への追加を行っている。

次をテンプレート引数などでコンパイル時に分ける。

- 固定幅か動的幅か
- 統計を取るか
- 全ターン重複排除を使うか
- 履歴を取るか
- ハッシュを再度混ぜるか

固定幅かつ統計不要の場合は、探索ループから時刻取得、平均計算、履歴更新をすべて外す。

## 実装順

1. `push_lazy` を使う。
2. ハッシュ表の事前確保条件と容量を直す。
3. セグメント木の全初期化をやめる。
4. 脱落済み `new_candidates` を並べ替え前に除去する。
5. 古い値を位置指定で無効化し、生存W件だけで定期的に表を作り直す。
6. 全ターン重複排除用の表を分離する。
7. 採否決定後にだけ `Action` を保存する。
8. 次世代の最終位置へ `Action` を直接保存する。
9. 親番号による配列振り分けへ変える。
10. 固定長ブロック方式の `Action` 保管領域へ変える。
11. `TreeNode`、`ActionId`、候補構造体を縮める。
12. 固定幅専用経路と、実行傾向を利用するコンパイル最適化を適用する。

目標は、一時採用された候補を無制限に残す構造ではなく、Wに比例する量だけを管理し、採用位置が決まった `Action` だけを保存する構造である。

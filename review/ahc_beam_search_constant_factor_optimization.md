# ビームサーチ・ライブラリの高速化案

## 追加の高速化案 (2026-09-03)

以下は正しさの問題を修正した後に検討する案です。ベンチマークは実行していません。採用の前後で、同じ入力と乱数のシードに対する得点、操作列、終了状態、`turns_done` が変化しないことを確認します。同点時の順序や、時刻を取得する頻度を変更する案では探索結果も変化し得るため、別の設定として計測します。

### 優先度 高

1. `beam_search_turn.cpp:181-220,343-350,795-815` と最適化版 `:383-396,833-855` は、一時的に採用された後に同じハッシュ値の候補へ置換されたものや、最悪の候補として除外されたものも `new_candidates` に残します。ソートの前に、生存フラグが立っている候補だけを先頭へ詰め、脱落した候補の `ActionId` を解放します。最適化版の既定の処理では `candidate_group_ends` (`:466-472,845-855`) を使用するため、親ごとに詰めた上で各親の終端位置も求め直します。同点時の順序は現行どおり維持します。
2. `candidates.cpp:92-97,139-180,287-327` は除外した候補のハッシュ値を値 -1 の削除済みの印として残すため、表の大きさが現在の幅 O(W) ではなく、一時的に採用した候補の総数まで増加します。削除済みの印の割合が増えた時点で、生存している候補だけを残して表を再構築します。
3. `candidates.cpp:176-178,322-324`, `naive_beam_search.cpp:115-117` の `inner_len()==1` という事前確保の条件は、最小容量が 16 であるため成立しません。必要な容量との比較に修正します。
4. SA 側の項目ですが、同じ AHC で高頻度に実行される処理として挙げます。統計が不要な設定では、`sa/sa.cpp:46-48,80,82,84-86,90,233-234,260,263,265-267,271,370-374,436,443-444` の表示専用の統計を省略します。探索の入力である `iter` は省略しません。
5. 通常版 `beam_search.cpp:471-475` と合成版 `beam_search_compose.cpp:581-586` の親番号による全体のソートは、親番号が連続しているため、順序を維持する計数ソートに置き換えることができます。

### 優先度 中

1. `beam_search.cpp:77-94` と合成版 `beam_search_compose.cpp:170-190` では、候補用の領域と世代ごとの領域の両方に `Action` を保存しています。この箇所を、最終的な位置に直接構築する方法に変更します。
2. `beam_search_turn_optimized.cpp:466-472` は `vector` の再確保を避けるため、親の `Action` を展開のたびにコピーします。再配置されない固定長の領域に保存すれば、参照を保持することができます。
3. `candidates.cpp:153-161,299-307` はセグメント木の全体を毎回初期化した後に内部ノードを再構築します。生存している葉に値を設定し、未使用の葉だけを単位元にすれば十分です。ターン指定版は既にこれに近い実装になっています。`naive_beam_search.cpp:93-101` は `set` で逐次更新しており、内部ノードに前のターンの値が残るため、この変更をそのまま適用することはできません。世代番号を付ける方法か、変更された部分木だけを再構築する方法を別の案として検討します。
4. 幅が固定で呼び出し側も統計を使用しない専用の実装では、ターンごとの時刻の取得、`width_hist`、平均値の更新をコンパイル時に省略します。公開される `BeamParam` の統計値は変化するため、明示的に選択する設定にします。
5. 履歴に残す生存中の番号の `unordered_set` は、通常版 `beam_search.cpp:202-213`、合成版 `:311-322`、親番号版 `:267-276`、圧縮版 `:264-273` では番号の上限が既知であるため、各番号について最後に印を付けた世代を保存する配列に変更することができます。活動中の番号の出力順は変化し得ます。
6. StatePool の空き番号の一覧を、`reserve` 済みの `vector` に対する末尾への追加と末尾からの削除で管理する方式に変更し、二重解放を防ぐ使用中フラグも連続した領域に配置します。

旧版は保守の対象外として、高速化の対象から除外します。維持する場合は、`old/beam_fast_old.cpp:168-181,253,285-292`, `old/beam_search.cpp:449-454`, `old/beam_search_turn_old.cpp:604-618` の全体のソートと予約容量の不足を別途修正します。

以下の旧提案のうち、通常版の `push_lazy`、最適化版で採用後に行う `Action` の確保、親ごとの境界の管理、`TreeNode` の縮小は既に実装済みです。現行の実装で残っている項目だけを上の順で計測します。

## 高速化の対象

- `beam_search.cpp`
- `beam_search_turn.cpp`
- `candidates.cpp`
- `hash_dict.cpp`

問題固有の `State`、単純版、compose 版、radix 版は対象外とします。

## 優先順位

1. 候補のハッシュ表を W に比例する大きさに制限します。
2. 脱落済みの候補を並べ替えより前に除去します。
3. `Action` は候補への採用が確定してから保存します。
4. 親番号による並べ替えを配列への振り分けに置き換えます。
5. `Action` の保管場所を固定長ブロック方式にします。
6. 木や候補の構造体を小さくします。
7. 固定ビーム幅では時刻の計測と統計処理を省略します。

## 挙動への影響

| 改善 | 探索結果への影響 |
|---|---|
| 古い値を、位置を指定して無効化し、定期的に表を再構築する | 変化しない。値 `-1` と同じ規則を維持する |
| ハッシュ表の容量変更、再度混ぜる処理の省略 | 変化しない。格納位置だけが変化する |
| 全ターンをまたぐ重複排除用の表を分離する | 現在の `-2` と周期的な初期化の規則を再現すれば変化しない |
| 脱落済みの候補の早期除去 | その時点で生存している候補の集合は変化しない。同点の候補の順序が変化すると、後の探索結果は変化し得る |
| `Action` の保存を採用後へ遅らせる | 変化しない。ただし `Action` が通常の値型であることを前提とする |
| 次世代の最終位置へ `Action` を直接保存する | 変化しない。構築と破棄の時期だけが変化する |
| 親番号による配列への振り分け | 同点の候補の順序まで再現すれば変化しない。再現しなければ後の探索結果は変化し得る |
| 良い候補から先に展開する | 変化し得る。乱数の消費順と同点の候補の採否も変化するため、オプションの機能にする |
| 固定長ブロック方式による `Action` の保管 | 変化しない。`Action` を参照経由で変更しないことを前提とする |
| 構造体と `ActionId` の縮小 | 値が収まり、ビット詰めが正しければ変化しない |
| セグメント木の初期化範囲の削減 | 未使用の葉を正しく初期化すれば変化しない |
| 固定幅専用の処理 | 幅の調整と統計が無効な場合に限れば変化しない |

挙動を完全に維持する場合は、候補に列挙順の番号を付け、`(親番号, スコア, 列挙順番号)` で比較します。これにより、脱落した候補を先に除去しても、生存している同点の候補の順序を固定することができます。

ただし、現在の `std::sort` は同点の要素の順序を保証しません。現在の候補の順序まで完全に固定するには、現行の実装にも列挙順の番号を追加し、比較の規則を明文化する必要があります。

## 1. 候補のハッシュ表

現在は最悪の候補を除外しても、古いハッシュ値を値 `-1` として表に残しています。このため、表の要素数が一時的に採用された候補の数まで増え、再構築と初期化にかかる時間が長くなります。

単純な削除機能の追加は第一候補ではありません。開番地法では削除済みの印の管理や後続の要素の移動が必要になり、削除自体にもコストがかかります。

位置を指定して無効化し、定期的に一括で再構築する方法を推奨します。

- 各候補にハッシュ表内の位置を保存します。
- 除外するときは、ハッシュ値を再探索せず、その位置の値を直接 `-1` にします。
- 表の容量は約 4W に固定します。
- 使用済みの位置が約 2W まで増えた時点で、生存している W 件だけで表を再構築します。
- 現在の候補を管理する表と、全ターンをまたぐ重複排除用の表を分離します。
- `State` が十分に拡散されたハッシュ値を返す場合は、`HashDict` 内でハッシュ値を再度混ぜないようにします。

現状の `func.set(old_hash, -1)` も古いハッシュ値を再探索しています。位置を指定した無効化では、この探索を 1 回減らすことができます。一括再構築は W 回程度の置換につき 1 回、W 件を連続して再挿入する処理であるため、置換 1 回当たりでは定数時間になります。

この方式では、置換が少ない場合は再構築が発生せず、置換が多い場合も表の大きさを W に比例する範囲に抑えることができます。現在の `HashDict` の連続領域と 16 要素の同時比較も維持できるため、削除機能を追加する場合より定数倍が小さくなると考えられます。

`Candidates::reset` の `func.inner_len() == 1` は、初期容量が 16 であるため成立しません。また、`HashDict(8W)` は内部で約 16W 以上を確保するため過剰です。

## 2. 脱落済みの候補の早期除去

可変ターン版は、一度採用された候補をすべて `new_candidates` に追加します。後から除外された候補も、並べ替えと木の更新まで残ります。

候補を列挙した後、並べ替えを行う前に脱落済みの候補を除去します。

```cpp
int dst = 0;
for (auto &c : new_candidates) {
    if (is_survived_node[c.aid]) {
        new_candidates[dst++] = c;
    } else {
        arena_release(c.aid);
    }
}
new_candidates.resize(dst);
```

さらに改善する場合は、各候補集合で最終的に生存している候補だけを列挙後に収集します。一時的に採用されただけの候補は、最初から `new_candidates` に追加しないようにします。

## 3. Action の保存の遅延

通常版は既存の `push_lazy` を使用せず、`Action` を値渡ししています。枝刈りの基準値やハッシュ値の重複により不採用になる候補にも、コピーが発生する可能性があります。

処理を次の 2 段階に分けます。

1. スコア、ハッシュ値、親番号だけで採否と格納位置を決定します。
2. 採用された場合だけ、その位置へ `Action` を保存します。

可変ターン版でも、`arena_put_reserve()` の呼び出しを候補の採用後に移動します。これにより、不採用になる候補に対する空き番号の取得と返却が不要になります。

## 4. Action の二重保存の解消

通常版は `Action` を一度 `candidates.next_beam` に保存し、`finalize_generation` で `gblock` へ移動しています。

次世代の保管領域を先に W 件分用意し、候補の格納位置と `Action` の格納位置を一致させます。採用時に最終位置へ直接保存すれば、世代の確定時に整理する対象はスコアや親番号だけになります。

スコア、ハッシュ値、親番号、`ActionId` と、`Action` 本体は別々に保管します。候補の管理中に大きな `Action` を読み込まないようにします。

## 5. 並べ替えの削減

`parent_leaf` と `par` は 0 から始まる密な整数です。このため、全候補を比較によって並べ替える必要はありません。

1. 親ごとの候補数を集計します。
2. 累積和で各親の格納位置を求めます。
3. 候補を親ごとの区間へ振り分けます。
4. 同じ親の区間の中だけをスコア順に並べ替えます。

同じ親の候補が少ない場合は、汎用の `std::sort` より次の方法が高速です。

- 2 件：1 回の比較交換
- 少数：挿入ソート
- 多数：`std::sort`

通常版はスコアの昇順に並べ替えた後、末尾から展開しているため、同じ親では悪い候補から展開しています。完全な再現性が不要な場合は、良い候補から展開して枝刈りの基準値を早く下げます。

## 6. Action の保管場所

可変ターン版は、`action_pool` の再確保で参照が無効になるため、展開する葉の `Action` をコピーしています。

`Action` を、移動しない固定長ブロックへ保存します。

- ブロック長は 2 の冪にします。
- `ActionId` にブロック番号とブロック内の位置を詰めます。
- 空いた `ActionId` は一覧に保持して再利用します。

これにより、`Action` を参照したまま `apply_op`、候補の列挙、`rollback` を実行することができます。

## 7. 構造体の縮小

- `TreeNode` の種類を `aid` の上位ビットへ詰め、16 バイトから 12 バイトに縮小します。
- `ActionId` は、最大ターン数と最大幅が収まる場合は 64 ビットから 32 ビットに縮小します。
- `record_history=false` では履歴用の `node_id` を構造体から完全に削除します。
- セグメント木の `pair<ScoreType,int>` は、余白が生じない専用の構造体にします。
- `Candidates::reset` ではセグメント木全体を初期化せず、未使用の葉だけを初期化します。

## 8. 固定ビーム幅専用の処理

`is_adjusting=false` の場合でも、各ターンで時刻の計測、平均の更新、`width_hist` への追加を行っています。

次の項目をテンプレート引数などでコンパイル時に切り替えます。

- 固定幅か動的幅か
- 統計を取得するか
- 全ターンをまたぐ重複排除を使用するか
- 履歴を記録するか
- ハッシュ値を再度混ぜるか

固定幅かつ統計が不要な場合は、探索ループから時刻の取得、平均の計算、履歴の更新をすべて除去します。

## 実装順

1. `push_lazy` を使用します。
2. ハッシュ表の事前確保の条件と容量を修正します。
3. セグメント木全体の初期化を廃止します。
4. `new_candidates` 内の脱落済みの候補を並べ替えの前に除去します。
5. 古い値を、位置を指定して無効化し、生存している W 件だけで定期的に表を再構築します。
6. 全ターンをまたぐ重複排除用の表を分離します。
7. 採否の決定後にだけ `Action` を保存します。
8. 次世代の最終位置へ `Action` を直接保存します。
9. 親番号による配列への振り分けに変更します。
10. 固定長ブロック方式の `Action` の保管領域に変更します。
11. `TreeNode`、`ActionId`、候補の構造体を縮小します。
12. 固定幅専用の処理と、実行傾向を利用するコンパイル最適化を適用します。

目標は、一時的に採用された候補を無制限に残す構造ではなく、W に比例する量だけを管理し、採用位置が確定した `Action` だけを保存する構造にすることです。

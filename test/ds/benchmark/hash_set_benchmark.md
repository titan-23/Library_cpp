# HashSet の高速化の測定記録

2026-11-13 の記録です。titan_cpplib/ds/hash_set.cpp を対象にしました。

## 測定条件

- CPU は AMD Ryzen Threadripper 3990X (Zen 2)、コンパイラは GCC 12.3.0 です。
- ベンチマークは [hash_set_benchmark.cpp](hash_set_benchmark.cpp) です。各操作の内容はファイルの冒頭に記載しています。問い合わせは 200 万回です。
- `-std=c++20 -O2 -DNDEBUG -march=native` でのビルド (native) と、`-march` なしの既定ビルド (SSE2 まで) を計測しました。
- 変更前は HEAD (`9634bd5`) のヘッダです。CPU 4 に固定し、交互に 5 回ずつ実行して中央値を採用しました。
- 表の ns はキーが乱数の場合の値です。連番のキーでも短縮率は同程度でした。チェックサムは全行で一致しました。

## 方式の比較

試作した 4 方式を同じ条件で計測しました。ビルドは native で、表の値は ns/op です。容量はどの方式も要素数の 2 倍以上である 2 の冪で、最大の占有率は 1/2 です。

- 現行: 存在を表す bitset とキーの配列を保持します。キーは 1 個ずつ比較します。
- HashDict 型: HashDict から値を除いたものです。1 byte の制御配列を 16 個ずつ SSE2 で比較し、一致した位置のキーを参照します。
- 線形探査: キーの配列だけを保持し、0 で空きを表します。キーは 1 個ずつ比較します。
- 線形探査 + SIMD 探索: 配置は線形探査と同じで、contains だけ連続する 4 個のキーをまとめて比較します。

- HashDict 型は、テーブルがキャッシュに収まる大きさの場合は contains が高速です。探す位置のずれを SIMD の比較で吸収し、分岐予測が外れないためです。
- HashDict 型は、挿入と大きいテーブルでの contains_hit が低速です。制御配列を読み込んでからキーの位置が定まり、2 回の読み出しが直列になるためと考えられます。挿入では制御配列とキーの配列の 2 か所を更新します。
- HashDict 型は、大きいテーブルでの contains_miss だけは最も高速です。1 byte の制御配列だけを読み込めば十分であるためです。
- 線形探査は、挿入と大きいテーブルでの contains_hit が最も高速です。1 回の操作の命令数が少なく、複数の操作の読み出しが並行して実行されるためと考えられます。小さいテーブルでの contains は、分岐予測が外れるため低速です。
- 線形探査 + SIMD 探索は、挿入が線形探査と同程度で、contains は小さいテーブルで HashDict 型と同程度になります。この方式を採用しました。
- 挿入の探査も SIMD にした版と、64 byte 境界にそろえた 8 個を 1 組にして SIMD で比較する版も試しました。どちらも n=300000 以上で挿入が 1.4〜2.7 倍遅かったため、採用しませんでした。

## 変更点

- キーの配列だけを保持する線形探査にしました。0 で空きを表し、キー 0 は別の変数で保持します。
- 探査はテーブルの末尾で折り返さず、末尾の 64 個の余白へ続けます。余白の末尾の 4 個は常に空のまま維持し、4 個ずつの比較がテーブルの外を参照しないようにしました。余白をすべて使用した場合は容量を 2 倍にします。
- contains は連続する 4 個を simd_equal_bits で比較します。simd_equal_bits は others/simd_int.cpp に追加しました。SimdInt の SSE2 用の実装は 32 bit 整数だけを扱うため、64 bit 整数は 32 bit ずつ比較して上位と下位の結果の論理積を取ります。
- 再構築を noinline にしました。再構築がインライン展開されると挿入がインライン展開されなくなり、試作では大きいテーブルへの挿入が 1.5 倍遅くなりました。
- 既定ビルドでは contains がインライン展開されず、n=3000000 で 14〜19% 遅くなりました。そのため always_inline を付けました。
- ハッシュ関数を、HashDict と同じ 128 bit の積の上位と下位の xor にしました。128 bit の積を変数に格納すると、GCC 12 は SIMD を使用する関数で積をスタック経由で再度読み込みます。これを避けるため、上位と下位を別の式で求めています。
- salt はスレッドごとに 1 回だけ random_device から生成し、以後は分割した乱数列から取得します。現行は再構築と容量を指定した構築のたびに random_device を使用していました。8 要素の集合を作成すると 4 回使用し、集合 1 個あたり約 11 µs かかっていました。
- 容量を指定しない構築の初期容量を 1 から 16 に変更しました。再構築ではキーの配列を移動して使用し、複製しません。

## 不利になった点

- clear は、1 スロットあたり 1 bit の bitset ではなく 1 スロットあたり 8 byte のキーの配列を 0 で埋めるため、埋める領域の大きさが 64 倍になりました。容量に対して要素が少ないまま clear を繰り返す場合は遅くなります。
- n=3000000 の clear_cycle は 19〜21% 遅くなりました。clear の処理量の増加に加えて、新しいキーの挿入で大きなキーの配列を読み込むためです。現行は 1 MB の bitset だけを読み込み、キーは格納するだけでした。
- 既定ビルドの n=3000000 の contains_miss は 17% 遅くなりました。SSE2 での 64 bit 比較は命令数が多く、テーブルが大きいと読み出しが並行して実行されません。比較する個数を 2 個にすると大きいテーブルでは速くなりますが、小さいテーブルの contains_miss が 40〜60% 遅くなったため採用しませんでした。

## 検証

- [hash_set_random.cpp](../hash_set_random.cpp) で unordered_set と操作ごとに比較しました。テストには、キー 0 や 2^64-1 などの特別な値、偏ったキーの列、clear 後の再利用、容量を指定しない構築からの拡張が含まれます。
- native、既定ビルド、SIMD なし (`-U__SSE2__`)、AddressSanitizer と UndefinedBehaviorSanitizer 付きの native と既定ビルドの 5 構成でテストが成功しました。clang 14 でも成功しました。
- contains で空きの判定をキーの判定より先にする誤りと、SSE2 の 64 bit 比較で上位と下位の論理積を取らない誤りを入れると、テストが失敗することを確認しました。
- ライブラリ単体は C++17 と C++20 でコンパイルできます。

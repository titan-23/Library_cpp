# HashSet の高速化の測定記録

2026-11-13。titan_cpplib/ds/hash_set.cpp を対象にした。

## 測定条件

- CPU は AMD Ryzen Threadripper 3990X (Zen 2)、コンパイラは GCC 12.3.0。
- ベンチマークは [hash_set_benchmark.cpp](hash_set_benchmark.cpp)。各操作の内容はファイル冒頭に書いた。問い合わせは 200 万回。
- `-std=c++20 -O2 -DNDEBUG -march=native` (native) と、`-march` なしの既定ビルド (SSE2 まで) を測った。
- 変更前は HEAD (`9634bd5`) のヘッダ。CPU 4 に固定し、交互に 5 回ずつ実行した中央値。
- 表の ns は鍵が乱数のときの値。連番の鍵でも短縮率はほぼ同じだった。チェックサムは全行で一致した。

## 方式の比較

試作した 4 方式を同じ条件で測った (native、ns/op)。容量はどれも要素数の 2 倍以上の 2 冪で、最大の占有率は 1/2 である。

- 現行: 存在を表す bitset と鍵の配列。1 個ずつ比べる。
- HashDict 型: HashDict から値を除いたもの。1 byte の制御配列を 16 個ずつ SSE2 で比べ、一致した位置の鍵を読む。
- 線形探査: 鍵の配列だけを持ち、0 を空きの印にする。1 個ずつ比べる。
- 線形探査 + SIMD 探索: 線形探査の配置のまま、contains だけ連続する 4 個の鍵をまとめて比べる。

- HashDict 型は、表がキャッシュに収まる大きさでは contains が速い。探す位置のずれを SIMD の比較で吸収し、分岐予測を外さないためである。
- HashDict 型は、挿入と大きい表での contains_hit が遅い。制御配列を読んでから鍵の位置が決まり、2 回の読み出しが直列になるためと考えられる。挿入では制御配列と鍵の配列の 2 か所に書く。
- HashDict 型は、大きい表での contains_miss だけは最も速い。1 byte の制御配列だけを読めば済むためである。
- 線形探査は、挿入と大きい表での contains_hit が最も速い。1 回の操作の命令数が少なく、複数の操作の読み出しが重なるためと考えられる。小さい表での contains は分岐予測を外して遅い。
- 線形探査 + SIMD 探索は、挿入が線形探査とほぼ同じで、contains は小さい表で HashDict 型と同程度になる。これを採用した。
- 挿入の探査も SIMD にした版と、64 byte 境界に揃えた 8 個を 1 組にして SIMD で比べる版も試した。どちらも n=300000 以上で挿入が 1.4〜2.7 倍遅く、採らなかった。

## 変更点

- 鍵の配列だけを持つ線形探査にした。0 を空きの印に使い、鍵 0 は別の変数で持つ。
- 探査は表の末尾で折り返さず、末尾の 64 個の余白へ続ける。余白の最後の 4 個は常に空に保ち、4 個ずつの比較が表の外を読まないようにした。余白を使い切ったら容量を 2 倍にする。
- contains は連続する 4 個を simd_equal_bits で比べる。simd_equal_bits は others/simd_int.cpp に加えた。SimdInt の SSE2 段は 32 bit 整数だけを扱うので、64 bit 整数は 32 bit ずつ比べて上下の結果の論理積を取る。
- 再構築を noinline にした。再構築がインライン展開されると挿入がインライン展開されなくなり、試作では大きい表の挿入が 1.5 倍遅くなった。
- 既定ビルドでは contains がインライン展開されず、n=3000000 で 14〜19% 遅かった。always_inline を付けた。
- ハッシュ関数を HashDict と同じ 128 bit 積の上位と下位の xor にした。128 bit の積を変数に置くと、GCC 12 は SIMD を使う関数で積をスタック経由で読み直す。上位と下位を別の式で求めて避けた。
- salt はスレッドごとに 1 回だけ random_device から作り、以後は分割した乱数列から取る。現行は再構築と容量を指定した構築のたびに random_device を使っていた。8 要素の集合を作ると 4 回使い、1 個あたり約 11 µs かかっていた。
- 容量を指定しない構築の初期容量を 1 から 16 にした。再構築は鍵の配列を移動して使い、複製しない。

## 不利になった点

- clear は 1 枠 1 bit の bitset ではなく 1 枠 8 byte の鍵の配列を 0 で埋めるので、書く量が 64 倍になった。容量に比べて要素が少ないまま clear を繰り返す使い方では遅くなる。
- n=3000000 の clear_cycle は 19〜21% 遅い。clear の量に加え、新しい鍵の挿入で大きな鍵の配列を読むためである。現行は 1 MB の bitset だけを読み、鍵は書くだけで済んでいた。
- 既定ビルドの n=3000000 の contains_miss は 17% 遅い。SSE2 での 64 bit 比較は命令数が多く、表が大きいと読み出しが重ならない。比べる個数を 2 個にすると大きい表では速くなるが、小さい表の contains_miss が 40〜60% 遅くなったので採らなかった。

## 検証

- [hash_set_random.cpp](../hash_set_random.cpp) で unordered_set と操作ごとに比べた。鍵 0 や 2^64-1 などの特別な値、偏った鍵の列、clear 後の再利用、容量を指定しない構築からの拡張を含む。
- native、既定ビルド、SIMD なし (`-U__SSE2__`)、AddressSanitizer と UndefinedBehaviorSanitizer 付きの native と既定ビルドの 5 構成で通った。clang 14 でも通った。
- contains で空きの判定を鍵の判定より先にする誤りと、SSE2 の 64 bit 比較で上下の論理積を取らない誤りを入れると、テストが失敗することを確かめた。
- ライブラリ単体は C++17 と C++20 でコンパイルできる。

# 動的ビーム幅調整の改善案

対象は `beam_search.cpp`(通常版)と `beam_search_turn.cpp`(ターンスキップ版)。
目的は、TL ちょうどで探索を終えるようにビーム幅 W を毎ターン調整することにある。
本書は現状の失敗原因の分析と、置き換え案の設計を述べる。実装はしない。

## 現状の仕組み

### 通常版 (`beam_param.cpp` の `get_beam_width`)

- 10 ターンごとに幅を更新する。それ以外のターンは前回値を返す
- 単位コストを `time_sum / beam_width_sum`(開始からの累積平均)で見積もる
- 推奨幅 `pred_width = (残時間 / 残ターン) / 単位コスト` を出す
- 最終値は `(pred_width*2 + 過去の平均幅) / 3` のブレンド

### turn 版 (`compute_req_w` + `recommend_width`)

- 残メタターン数を `(max_turn - min_target_in_tree) / ema_step` で推定する
- active / empty メタターンを分け、active のコストを W に比例するとみなす
- コスト係数は開始からの累積平均 (`time_active_sum / count_active` など)
- 幅は `get_cands()` の **pool 生成時** に確定する

## 失敗原因の分析

### 両版に共通する構造的な問題

1. **累積平均は記憶が無限で、コストの変化に追従できない。**
   1 候補あたりのコストはターンとともに変わる。分岐数、状態サイズ、tour 長、
   rollback 深さが進行につれて増える問題が多い。開始からの平均は序盤に
   引きずられ、終盤の実コストを過小評価する。結果、W を絞るのが遅れて TL 超過するか、
   逆にどこかで一度絞った履歴に引きずられて W が戻らない。

2. **開ループ予測 + 反映遅れの組で、フィードバックが発散側に働く。**
   通常版では、ターン t で選んだ W はターン t+1 の展開コストを決める。
   一方 `timestamp()` は、ターン t の所要時間(実体は前世代の幅 W_{t-1} の展開コスト)を
   新しい `candidates.size()`(= W_t 側)に紐付けて記録する(`beam_search.cpp:428`)。
   W を下げた直後は「大きい dt ÷ 小さい W」で単位コストを過大評価し、
   次の推奨がさらに小さくなる。下降スパイラルの形になる。上げた直後は逆向きに過大推奨する。
   「上手く動くこともある」のは、幅が定常なら帰属ずれが消えるためと説明がつく。

3. **固定費の分離がない。**
   1 ターンのコストは `dt = a + b*W` の形をとる。`dt / W` を単位コストにすると、
   W が小さい領域で b を過大評価する(`b_hat = a/W + b`)。W が一度小さくなると
   過大な単位コストのせいで戻れなくなる。

4. **暴走時の安全装置がない。**
   予測が外れたときに TL 超過を防ぐ強制ブレーキも、
   時間が余ったときに使い切る仕組みもない。

### 通常版に固有の問題

- **過去平均幅とのブレンドが慣性になる。** `ave_beam_width` は開始からの平均で、
  初期値やキャリブレーション期間の幅を永久に引きずる。推奨値への収束を遅らせ、
  10 ターン周期の更新と合わさって振動や停滞を生む。
- **10 ターン周期が粗い。** ターン数が数百しかない問題では、調整機会が数十回しかない。
  超過に気づいてから絞るまでの遅れが致命的になる。
- **キャリブレーションがターン数基準。** 最初の 11 ターンを初期幅のまま走る。
  初期幅が過大だと、この期間だけで予算の大半を使い切る。失った時間は回収できない。

### turn 版に固有の問題

1. **幅の決定時点と消費時点が離れている。**
   pool の幅は `get_cands()` が pool を作った瞬間、すなわち
   その target_turn への最初の候補が push された時点で固定される。
   実際にその pool の leaf が展開されるのは何メタターンも後になる。
   制御工学でいうむだ時間が大きく、しかも可変なので、
   どんなコストモデルを載せても安定しない。turn 版が通常版より
   悪化しやすい最大の要因はここにある。

2. **残メタターン推定が壊れやすい。**
   `min_target_in_tree` の前進量は「最も遅れている生存枝」に支配される。
   ビームの大半が先へ進んでいても、遅い枝が 1 本残ると delta_target = 0 が続き、
   `ema_step` が縮んで remain_meta が膨張し、W が 1 に張り付く。
   逆に遅い枝が消えて min_target が跳ぶと W が急拡大する。
   平均進行速度で割るという推定自体が、この分布の裾に対して頑健でない。

3. **empty ターンのコストも一定でない。**
   empty メタターンの dt は tree 走査で、tree サイズに比例する。
   tree サイズは W と生存窓の長さで変わるのに、累積平均一本で扱っている。

## 設計方針

予測精度を上げる方向ではなく、**比率フィードバック制御**を核に据える。
理由は次の通り。

- 消費ペースと目標ペースの比だけを使えば、コストモデルの絶対値バイアスが打ち消される。
  `dt = a + b*W` の a を知らなくても、threshold 枝刈りによる非線形があっても、
  更新の符号は常に正しく、反復で不動点に収束する
- 更新率の上限(レートリミット)を入れれば、帰属ずれやむだ時間があっても振動しない
- 毎ターン更新できるので、コストのドリフトに自動で追従する

コストモデル(a + b*W の回帰)は捨てずに、キャリブレーション直後の
大きな初期補正にだけ使う。定常の追従は制御器に任せる。

## 提案 1: 共通コントローラ(両版)

毎ターン(turn 版はコスト計上のあった毎メタターン)、次を計算する。

```
dt_hat     = EMA(直近の 1 ターン所要時間, alpha = 0.2〜0.3)
budget     = time_limit - elapsed - reserve        // reserve は後述
target_dt  = budget / remain_costed_turns
r          = target_dt / dt_hat
W_next     = clamp( round(W_cur * clip(r, 1/rho, rho)), W_min, W_max )
```

- **rho(1 ターンあたりの変化率上限)は 1.3〜1.5。**
  むだ時間 1〜数ターンの系でも振動しない値をこの範囲から実測で選ぶ
- **`beam_width` は初期値であり、上限ではない。** 制御が必要と判断すれば
  指定幅を超えて広げる。上限・下限を課したい場合は別パラメータ
  `max_beam_width` / `min_beam_width` で指定する。既定は `min = 1`、
  `max = 無制限`。現行 turn 版の「指定幅を上限とする」挙動は廃止する
- **立ち上げは指定幅から始める。** 最初の数ターンだけ rho を 2 程度に緩め、
  指定幅が外れていても素早く補正する。過大側の失敗は時間を失って
  回収できないので、見当がつかない問題では低めの `beam_width` を渡す
  運用を推奨する。ライブラリ側で勝手に初期値を下げることはしない
- **固定ターン数のキャリブレーション期間は廃止する。**
  最初の 1 サンプルで EMA を初期化し、2 ターン目から制御する

### 帰属の修正

dt を「そのターンに実際に展開した親の数」に紐付ける。

- 通常版: `timestamp()` に渡す幅を `candidates.size()`(新ビーム)から
  そのターンの展開親数 `cand.size()` に替える
- turn 版: `expanded_leaf_count` を使う(現状すでに正しい)

比率制御では単位コストの絶対値は使わないが、
初期補正用の回帰と、ログの解釈のために帰属は正しておく。

### 安全装置

- **reserve**: TL の 2〜5% を経路復元と出力用に確保し、budget から先に引く
- **強制ブレーキ**: `elapsed + dt_hat * remain_costed_turns > time_limit` が
  成立したら、レートリミットを無視して `W_next = max(W_min, W_cur * r)` まで
  一気に絞る。残時間が dt_hat を下回ったら W = 1 に固定して完走を最優先する
- **終盤の使い切り**: 残りターンが少ない局面では rho の上側を緩め、
  余った予算を最終盤の幅に回す。メモリ上限には別途キャップを掛ける

### remain_costed_turns

- 通常版: `max_turn - turn`。正確な値がそのまま使える
- turn 版: 提案 2 で述べる

## 提案 2: turn 版固有の変更

### 幅の適用を消費時点に移す

pool 生成時の幅確定をやめ、**展開直前に上位 W 件へ切り詰める**方式にする。

- メタターン t の `get_next_beam` の前に、pool[t] の生存 entry に対して
  最新の推奨幅 W_t を計算する
- `pool.size() > W_t` なら score で `nth_element` し、
  溢れた entry の aid を非生存にして解放する。その後 tree を走査する
- pool 生成時の幅は「上限キャップ」として残す。
  値は `min(W_max, 直近推奨 * 1.5〜2)` 程度にし、メモリと push コストを抑える

これで幅の決定がコスト発生と同じメタターンに揃い、むだ時間が消える。
副作用として、push 時の threshold が実効幅より緩くなり try_op の受理が
やや増える。キャップを推奨幅に近づけて温まり次第絞れば影響は小さい。

### 残メタターン推定を直接カウントに替える

`ema_step` と `min_target_in_tree / ave_step` による推定を廃止する。
ループ構造から、コストが発生する残りイテレーション数は直接見積もれる。

- ループは turn を 1 ずつ進め、`min_target_in_tree > turn` のイテレーションは
  ほぼ無償でスキップされる
- したがって残りのコスト発生イテレーション数の上限は
  `U = max_turn - max(turn + 1, min_target_in_tree)`
- 過去の実績から `costed_rate = turn_sum / (turn + 1)`
  (timestamp_meta はコスト発生ターンでのみ呼ばれるので分子はそのまま使える)を取り、
  `remain_costed_turns = min(U, (max_turn - turn) * costed_rate)` とする

U は決定的な上限なので、推定が外れても TL 超過側には倒れない。
遅い枝 1 本に支配される `min_target` の前進速度と違い、分布の裾に対して頑健になる。

### active / empty の扱い

dt_hat は active / empty を混ぜた「コスト発生ターンあたり」の EMA でよい。
混合比が急変する問題では、現行の分離(active 率と各 dt)を
累積平均から EMA に替えて `dt_hat = rate * dt_active + (1 - rate) * dt_empty`
と合成する。分離自体の考え方は現行のままで、統計量の窓だけ直近化する。

## 提案 3: 終了状態必達・可変ホライズン問題への対応

max_turn が上限にすぎず、finished な State への到達が必須の問題では、
探索の実質ホライズンは「finish が最初に現れるターン」で決まる。
これはインスタンスと探索の質に依存し、探索中の見積もりも毎ターン変わる。
`remain = max_turn - turn` をそのまま使うと残ターンを過大評価し、
W が小さいまま TL を大きく残して終わる。逆に楽観的な見積もりを
そのまま信じると TL 超過に倒れる。次の三段で吸収する。

### State インターフェースの追加

```cpp
// この状態から finish までに要するターン数の見積もりを返す
// optional。requires で検出し、無ければ従来の max_turn ベースにフォールバックする
int estimate_remaining_turns() const;
```

- 厳密さは要求しない。**単調で、真の残りターン数におおむね比例していれば足りる。**
  スケールの狂い(常に 2 倍を返す等)は後述の較正で打ち消される
- 実装例: 残タスク数、残距離 ÷ 1 ターンの平均移動量、未処理要素数
- 呼び出し点は、展開する親状態へ apply した直後。全親で呼ぶとコストが
  幅に比例して増えるので、先頭 k 親のサンプリングでよい(k は 8 程度)

### 集約と較正

1. **集約は悲観側の分位点をとる。** サンプルの 75% 点程度を R_t とする。
   残りターンの過大評価は W が小さくなるだけで安全に倒れるが、
   過小評価は TL 超過につながる。この非対称のため悲観側に寄せる
2. **減少速度で較正する。** 予測器のスケールバイアスは
   `p = EMA(R_t - R_{t+1})`(1 実ターンあたりの予測減少量)で測り、
   `remain_hat = clamp(R_t / max(p, eps), 1, max_turn - turn)` とする。
   整合的な予測器なら p ≈ 1 で恒等になる。turn 版の min_target
   進行速度推定と同型の考え方だが、対象がビームの代表状態の予測値であり、
   最遅枝の前進に支配されない点で頑健
3. **揺れはレートリミットに吸収させる。** remain_hat が毎ターン変わっても、
   W の変化率は rho で抑えられているので発散しない。remain_hat 自体に
   軽い EMA を掛けてもよいが、残り十数ターンの終端域では平滑化を切り、
   遅れによる使い残しを避ける

### 制御器への接続

- 共通コントローラの `remain_costed_turns` を remain_hat に置き換えるだけでよい。
  EMA、レートリミット、reserve、強制ブレーキはそのまま使える。
  比率制御は remain の意味論に依存しない
- turn 版では `remain_costed_turns = min(U ベースの推定, remain_hat * costed_rate)`
  と組み合わせる
- 現行仕様では最初の finish で探索を打ち切って return する。この前提では
  予算を finish 到達ターンまでに配分すべきで、remain_hat がその見積もりに当たる。
  将来 finish 後も TL まで改善を続けるモードを入れる場合も、
  remain の定義を「TL までの見込み反復数」に差し替えるだけで制御器は共用できる

## 検討して採らなかった案

- **予測モデルの精緻化(a + b*W + c*tree_size の逐次回帰)**:
  むだ時間と帰属ずれが残る限り、モデル精度を上げても開ループでは安定しない。
  制御器の初期補正の補助としてなら将来入れる余地はある
- **総ノード数バジェット方式**(TL / 単位コストで総展開数を先に決めて均等配分):
  実装は最も簡単だが、単位コストのドリフトに弱い。
  比率制御が毎ターンやることの静的近似にすぎない
- **事前ドライラン(短時間走らせて幅を決めてから本走)**:
  TL の一部を捨てる上、序盤と終盤でコストが違う問題に対応できない

## 検証計画

- `width_hist` と毎ターンの dt を CSV に出し、幅の推移・終了時刻・振動の有無を見る
- 合成 State で確認する
  - 1 候補コストがターンに比例して増えるケース
  - 分岐数が途中で段差的に変わるケース
  - turn 版: 大きな target_turn 差分を混ぜて min_target が停滞するケース
  - 終了必達型: finish 到達で打ち切る合成 State に、バイアスとノイズを載せた
    `estimate_remaining_turns` を実装し、finish 時点の消費時間が TL 近傍に入るケース
- 合格条件
  - 終了時刻が `[0.93 * TL, TL]` に入る(終了必達型は finish 時点で判定する)
  - 幅が単調でない振動(周期的な上下)をしない
  - 固定幅を手で調整した基準と比べてスコアが劣化しない


## プロンプト

各フェーズでは、前のフェーズで判明した内容を引用しながら回答するよう促します。「なんとなく」や「一般論」による回答は禁止し、問題のどの性質から導いたかを必ず明示させます。

### フェーズ 1: 問題構造の抽出

#### 1-A: 複数の視点による再定式化

```
問題文からストーリーを除き、以下の視点で並行して再定義する (自然さの評価は不要で、並列に列挙することが目的):
1. データ構造 (配列/グラフ/グリッド/集合): 許される操作と制約
2. 最適化: 決定変数 / 目的関数 / 制約
3. 既知の問題への帰着 (TSP/割当/スケジューリング/被覆/区間/フロー等) を最大 3 つ
4. ゲーム木: 状態 / 行動 / ターン / 終了条件
複数の見方がある場合はそれぞれ別に提示する。
```

#### 1-B: 最適解の形の逆算

```
理論的な最適解 (または上位陣が得ると想定される解) の構造を予想する:
- 特徴的な配置 / 順序 / 形状
- 先に決定しておくべき変数 (決め打ちすれば残りが従属する変数)
- 不変条件 / 対称性
- ランダムな解と区別できる特徴量
- (必須) 上位陣の想定スコアから「1 要素あたりの許容操作量」を概算し、必要な償却率 (1 操作で同時に進めるべき要素数) を見積もる。償却率 > 1 の場合、要素ごとの処理は原理的に不可能 → 「1 操作で多数の要素を同時に前進させる構造」が最適解の核心であると先に断定し、その構造/操作の候補を挙げる (1-D と関連付ける)。

3 つ以上挙げ、それぞれについて根拠 + 確信度 (5 段階) + 導出元の問題の性質を明示する。
```

#### 1-C: 変数の依存関係による分解

```
決定変数を列挙し、「ある変数を固定→残りが自明な問題/古典的な問題に帰着」する分解を 3 つ以上挙げる:
例: 順序を固定→各操作を貪欲に決定 / 最終配置を固定→最短経路 / 集合を固定→DP / 大域構造 (レイアウト・資源配置・経路割当) を固定→割当・スケジューリング
最低 1 つは「問題文に無い大域構造そのもの」を固定する分解を含める。
各分解について: 固定する変数の空間のサイズ / 固定後の帰着の可否・計算量 / 残りが探索なしで確定するか (閉形式・多項式時間アルゴリズム・厳密なルール)。
探索なしで確定する分解は構築解の第一候補として明示する。固定すべき変数は後段 (焼きなましの解表現/ビームサーチのノード情報) で再利用する。
```

#### 1-D: 操作の代数的性質

```
許される操作の集合を分析する: 可逆性 / 可換性 / 冪等性 / 生成性 (極小生成集合) / 不変量 / 対称性。
各性質を必ず両面から分析する (片面のみでは不完全): ①制約 = 禁止される遷移・到達不能 ②レバー = その性質を利用すると「コスト 0/低コスト」になる解表現・構造・操作単位は何か。
不変量・対称性・冪等性は否定形で終えず、必ず肯定形 (これを保持する構造を設計すれば〜が一括で定まる) に反転させる。
1 操作で多数の決定変数が同時に変化する場合は、その「1 回の適用」を探索の 1 ステップではなく構築のプリミティブの候補として明示する。
出力: 探索空間の縮約案 / 枝刈り条件 / 不変量の保持を前提とする解表現の候補。
```

#### 1-E: 入力構造の確認

```
入力の生成過程・分布から次を確認する:
- 入力の規模 (ランダム探索 / 簡易な焼きなまし / 貪欲のどれが現実的か)
- 統計的な偏り (密度 / クラスタ / 相関)
- ケース間の難度の差を左右する特徴量
- 制約のサイズと時間制限から求まる「1 状態あたりの計算量の予算」
→ 全ケースで共通の戦略で十分か、ケースの分類が必要かを判断する。
```

#### 1-F: 中間目標

```
初期状態↔目標状態の間に置く「中間目標」の案を、理由とともに挙げる。1-B の最適解の形と整合させ、各案について次を示す:
- 達成後に残りをルールベース/貪欲で完成させることができるか
- そこから目標までに後戻りが発生しないか
```

#### 1-G: 人間のヒューリスティクスの言語化

```
十分に賢い人間が手作業で解くときのヒューリスティクスを、実装可能なルール/評価値として言語化する。小さな例 (N=5 等) を手動でシミュレーションし、意思決定の基準を抽出してもよい。
```

### フェーズ 2: 大方針

#### 2-A: 素朴に適用した場合の適合度の判定

```
フェーズ 1 を踏まえ、素朴に適用した場合の適合度を判定する: 1. 貪欲 2. ビームサーチ 3. 焼きなまし
判定軸 (各軸でフェーズ 1 の記述を引用する):
- 途中状態を評価できるか (貪欲/ビームサーチの前提)
- 解全体の一括保持・意味のある近傍の定義が可能か (焼きなましの前提)
- 文脈の強さ (序盤が終盤を強く制約する = ビームサーチ向き)
- 後戻りの必要性 (= 焼きなまし向き)
- 下界の見積もりやすさ (ビームサーチの枝刈りの強さ)
- 基本操作のレバレッジ: 1 操作が解/多数の変数をどれだけ変化させるか。極端に高い場合は探索が細切れになり弱い (1-D の構築プリミティブに対応) →「その操作を軸に大域構造を構築して固定し、残りを割当/スケジューリング」を対案として必ず併記する。
各案について ○/△/× と判定根拠・最大の障害を示す。
```

#### 2-A': 成立条件の探索

```
2-A で △/× となった案について、「成立させる工夫」を必ず考える (「無理」と判断するのは最終手段とし、安易に候補から外さない)。

- 焼きなまし: 解表現の変換 (行動列→中継点/順序/集合/決め打ち変数列、1-C の固定変数列、1-B の最適形のパラメータ化) / 探索空間の制限 (損な解・対称解の除外) / 部分問題への限定 / 評価の代替 (近似・下界・緩和)
- ビームサーチ: 世代の自作 (1 つ決める単位) / 粒度の変換 (ミクロ⇔マクロ) / 評価の補強 (未来予測・下界・ロールアウト) / 同一視のためのハッシュ / 部分問題への限定
- 貪欲: 評価の階層化 (主評価+タイブレーク+乱択) / 多スタート+上位の採用 / マクロ単位の貪欲

各工夫について: 何を変更すると成立するか / 2-A の △× の根拠が解消されるか / 変換のコストと情報の損失 (最適性を失うか) / 再評価 ○/△/×。
混合戦略 (ビームサーチで初期解→焼きなまし等) も具体化する。
```

#### 2-B: スコアへの影響が最も大きい設計判断

```
2-A' の再評価後に推奨するアプローチを 1 つ選び、スコアを最も左右する設計判断を 1 つ特定する。2〜3 案を比較し、フェーズ 1 の根拠に基づいて 1 案を選択する。
判断項目の例:
- ビームサーチ: 世代の粒度 (ミクロ/マクロ、1-B の最適形と整合) / ノード情報を同一視する粒度 (1-C の固定変数) / 評価 (確定スコアのみ/下界を加算/ロールアウト)
- 焼きなまし: 解表現 (そのまま/1-C の固定変数列/中継点列) / 近傍 (評価値の変化が階段状にならない最小単位) / 評価 (厳密/近似/緩和)
- 貪欲: 評価の階層化 / 多スタート分散
形式: 判断項目 / 案 A, B, C / 長所と短所 / 採用案 / 根拠。
```

#### 2-C: 上位陣が採用すると想定されるアプローチ

```
上位一桁の解は非自明な工夫を 1 つ以上含む (特に 2-A' で我々が出せなかった解表現/粒度の変換)。候補を 3 つ挙げる:
- 独自の解表現 (問題文に無い抽象化) / 帰着による計算量の削減 (1-A) / 操作の代数的性質による空間の縮約 (1-D) / 情報量の多い評価 (複数のロールアウトの平均・二段階) / 入力分布に応じたケース別の戦略 (1-E) / 最適形から導く強い制約 (1-B) / 一見不向きな手法を成立させる解表現 (2-A' の延長)
各候補について: なぜ有効か (フェーズ 1 で判明した内容と関連付ける) / 実装の難度 / 素朴な方法と比較したスコア改善のオーダー。
最後に最も有望な候補を 1 つ選ぶ。
```

#### 2-D: 最終的な推奨方針

```
最終方針を 1 つ決定する:
- 概要 (2〜3 行) / 状態・解表現 (具体的に) / 行動・近傍 / 評価関数 (式または擬似コード) / 期待されるスコアの範囲 / 最大の懸念と切り替え先の次善策 / 採用しなかった 2-A' の工夫による改善の余地
方針が外れる可能性が最も高いシナリオを 1 つ挙げ、対処も併記する。
```

### 補助プロンプト

大方針が確定した後に必要に応じて使用します。

#### 評価関数の特徴量の検討

```
この問題の評価関数を考えます。以下の 3 つの観点から特徴量を提案してください。
- 局所的な盤面の良さ
- 次のターンの操作のしやすさ
- 目的の達成を阻害する度合いの定量化
```

#### 緩和問題による下界の設計

```
手数/スコアを最も悪化させる制約・ペナルティを 1〜2 個特定し、それを一切考慮しない (コスト 0, 容量 ∞, ワープ可) 緩和問題を作成する。緩和した問題で現状→目標 (最適) に至る最も単純なロジックと、最小手数 (最大スコア) の式を導出する。
式は「1 要素あたり」ではなく「1 操作で同時に影響を与えることができる最大数 (バッチ) あたり」で立てる。レバレッジの高い操作があるにもかかわらず要素ごとの和で下界を作ると、下界も評価も op の共有を構造的に考慮できなくなる。立てた下界と採用予定の評価/ポテンシャルが整合しているかを必ず確認する (要素ごとのコストなのに真の下界がバッチ単位である場合は、緩和の取り違えである)。
この下界を「理想状態までの距離」として評価関数に組み込む案も提案する。
```

# 貪欲法の派生と評価関数設計 指南書

AHC 等のヒューリスティック問題で用いる貪欲法の派生体系と、それを動かす評価関数の設計原則を整理する。自分の見直し用、および AI に渡す参照ドキュメント用。

過去改変貪欲については別ドキュメント `past_modification_greedy_guide.md` を参照。

---

## 第1部：貪欲法の派生

### 1.1 貪欲法の基本構造

貪欲法は、解を逐次的に構築する手続き。各ステップ t で：

1. 現状態 `s_t` から到達可能な候補 `{c_1, c_2, ...}` を列挙
2. 評価関数 `f` で各候補をスコアリング
3. 最良の候補を1つ選んで確定
4. `s_t → s_{t+1}` に遷移

派生は次の3軸で生まれる：

- **何を評価するか**：現在の利得か、未来の見込みか、過去への影響か
- **過去・未来をどこまで見るか**：現在のみ／k 手先まで／最後までシミュレーション
- **過去をどう扱うか**：触れない／編集する／後悔として測る

### 1.2 思考の型：本質的な貪欲を作るための視点

貪欲法の質は、評価関数 `f(現状態, 候補) → スコア` の設計で決まる。`f` をどう作るかは、次の思考の型のいずれか（または複数）から発想する。

#### 型1：最終目的からの逆算

最終的に何が成立すれば勝ちかを起点に、現在の1手を「勝ちにどれだけ近づくか」で評価する。A* のヒューリスティック関数の発想。

- 起点：「この問題で勝ち＝何が成立した状態か？」「勝ちに必要な要素を、現状はどれだけ持っているか？」

#### 型2：希少性に注目する

「今しか取れない」「今が一番安い」ものを優先する。リソースが時間とともに失われる構造を見つける。後悔ベース貪欲の核。

- 起点：「現在の選択肢のうち、時間とともに失われるものは何か？」「コストが将来上がるものは何か？」

#### 型3：自由度・制約に注目する

最も自由度の低い部分から先に決める。決めることで他の自由度が変わるなら、影響が大きい順に確定する。

- 起点：「現在、最も自由度が低いのは何か？」「それを先に決めると、後がどう楽になるか？」

#### 型4：ボトルネックから攻める

最終スコアを支配するボトルネックを特定し、そこから設計する。平均改善ではなく一点突破。

- 起点：「最終スコアを悪化させる最大要因は何か？」「それを小さくする1手は？」

#### 型5：可逆性で並べる

取り消しにくい決定を先に・慎重にする。軽い決定は早めに済ませる。

- 起点：「この決定は、後から覆せるか？」「覆せないなら、本当に今でいいか？」

#### 型6：対称性・等価性を畳む

結果が同じになる選択を1つにまとめる。状態空間を縮約し、計算リソースを温存する。

- 起点：「この選択肢の差は、結果に効くか？」「効かないなら、好きなものでよい」

#### 型7：単調性の利用

単調に増減する量を見つけ、その量で順序付ける。順序の概念を意識的に設計する。

- 起点：「2つの要素を入れ替えても解は同じか、どちらかが必ず良いか？」「単調に処理できる順序は存在するか？」

#### 型8：「もし全部入れたら」からの引き算

制約を無視した理想解を作り、そこから現実に引き戻す。上界からの構築。

- 起点：「制約がなければ最良解は何か？」「制約はどこを壊すか？」

#### 型9：交換不変量の発見

2要素を交換しても損しない／必ず得する条件を見つけ、その条件で並べる。exchange argument の発想。

- 起点：「最適解の中で、2つの隣り合う要素を交換したらどうなるか？」「常に得する条件はあるか？」

#### 型10：「最後の1手」から考える

終端から逆順に組み立てる。終端の構造が見えやすい問題で有効。

- 起点：「終了直前の状態は何か？」「そこに至るには、その1手前は？」

### 1.3 詰まりやすい点と処方

「本質的な貪欲が出ない」典型的な原因。

- **短期利得しか見ない**：型1 が欠けている → 評価関数に必ず「将来予測項」を加える
- **処理順序を疑わない**：型3, 7 が欠けている → 「どの順で処理すべきか」を必ず問う、順序自体が決定変数
- **選択の影響範囲が見えない**：型3 が欠けている → 1つ決めた後、他候補のスコアがどう変わるかを意識する
- **希少性を意識しない**：型2 が欠けている → 候補ごとに「今選ばないとどうなるか」を問う
- **ボトルネックを見ない**：型4 が欠けている → 「現解の質を決めている部分はどこか」を毎回特定する

### 1.4 新問題への思考フロー

新問題を見たら、次の順で考える：

1. **勝利条件の特定**（型1）：何が成立すれば最高スコアか
2. **ボトルネックの特定**（型4）：何が最終スコアを決めるか
3. **処理順序の検討**（型3, 5, 7）：要素はどの順で扱うべきか
4. **評価関数の設計**：短期利得 + 将来予測 + 制約ペナルティ
5. **希少性の確認**（型2）：「今しか取れない」候補はあるか
6. **交換不変量の確認**（型9）：順序の最適性は説明可能か

このフローを意識すると、「短期利得だけ見る貪欲」から脱却しやすい。

### 1.5 派生一覧

#### A. 通常貪欲（Pure Greedy）

各ステップで現在の利得が最大の候補を選ぶ。過去は触らず、未来は見ない。

- 長所：実装が単純、高速
- 短所：局所最適に陥りやすい
- 用途：問題の構造が素直で、現在の良さが将来も良さにつながる場合

#### B. ランダム貪欲（Randomized Greedy）

候補をスコア順に並べたうえで、上位 k 個からランダムに選ぶ、または確率的に選ぶ。

- 多始点と組み合わせて多様な初期解を作るのに有効
- 焼きなましの初期解生成として頻出

#### C. 後悔ベース貪欲（Regret-based Greedy）

候補ごとに「今これを選ばなかったら、後でどれだけ損するか」を計算し、後悔の大きいものから優先的に選ぶ。

- 「今しか取れないもの」を見落とさない発想
- 挿入問題、配車計画（VRP）などで有名
- 評価関数に「best - second_best」のような差分を組み込むのが典型

#### D. Look-ahead 貪欲

候補ごとに k 手先までシミュレーションし、k 手後のスコアで評価する。

- k=1 なら通常貪欲、k を増やすほど計算量と精度が上がる
- 計算量爆発を防ぐため、k 手先の評価は近似でも良い
- 後述の MCTS / Roll-out 貪欲に連続的に繋がる

#### E. Roll-out 貪欲（Roll-out / Simulation Greedy）

候補ごとに、その先を最後までランダム or 簡易貪欲でプレイアウトし、最終スコアで評価する。

- MCTS の簡易版
- 確率的問題、ゲーム木探索系に強い
- プレイアウトのコストが高いので、候補数や反復回数とのトレードオフ

#### F. 過去改変貪欲（Past-Modification Greedy）

現在の操作を実行するため、過去の操作列に挿入・置換・削除を加える。詳細は別ドキュメント参照。

- 過去への編集を伴う点で、他の派生と本質的に異なる
- 操作の可換性が高い問題で特に強力

#### G. 入れ替えながら貪欲（Swap-while-greedy）

構築の途中で、既に決めた要素同士を入れ替えることを許す。過去改変の「置換型」の局所版。

- 完成後の局所探索を構築中に行うイメージ
- 過去改変ほど大胆な編集はしないが、軽い修正で改善が得られる

#### H. 制約伝播ベース貪欲（Constraint Propagation）

「最も自由度の低い要素」「最も決定的な選択」から先に決める。1つ決めるごとに他の要素の選択肢を絞り込み、その情報を次の選択に活かす。

- 配置問題・パズル系で有効（ナンプレ、N-Queens、グラフ彩色）
- 「決まりやすいところから決める」逆貪欲的な発想

#### I. 多段階構築貪欲（Multi-stage Greedy）

問題を時間的・空間的・抽象度別に分け、段階ごとに貪欲を回す。

- 「先に骨組み、後で細部」
- 「粗いグリッドで決めて、細かいグリッドで精緻化」
- 各段階の評価関数が異なる場合が多い

#### J. 挿入ヒューリスティック（Insertion Heuristic）

未確定要素を1つずつ、現在解の最適な位置に挿入していく。

- Nearest Insertion / Farthest Insertion / Cheapest Insertion など
- TSP、スケジューリングで古典的
- 過去の決定の中身は変えない（過去改変との違い）

#### K. 後悔挿入（Regret Insertion）

挿入ヒューリスティックと後悔ベース貪欲の融合。「最良の挿入位置」と「次善の挿入位置」のコスト差が大きい要素から優先して挿入する。

- VRP 等で実用的に強い
- 「今挿入を後回しにすると損する要素」を優先する発想

#### L. 逐次破壊再構築（Construct-Destroy-Reconstruct）

通常貪欲で初期解を作り、一部を破壊して同じ貪欲で再構築する。

- LNS（Large Neighborhood Search）と接続
- 多始点的な探索になる

### 1.6 派生の選び方

問題を見たら、次の順で派生を選ぶ：

1. **過去への編集に意味があるか** → あれば過去改変貪欲（F）
2. **未来の見込みが現在の決定を変えるか**
   - 「今しか取れない」がある → 後悔ベース（C, K）
   - k 手先まで読めば判断できる → Look-ahead（D）
   - プレイアウトで評価できる確率的問題 → Roll-out（E）
3. **問題に明確な構造があるか**
   - 配置・パズル系で自由度に偏りがある → 制約伝播（H）
   - 階層的に分解できる → 多段階構築（I）
   - 順序の最適化が中心 → 挿入ヒューリスティック（J, K）
4. **多様な初期解が欲しい** → ランダム貪欲（B）
5. **構築済みの解の修正を許す** → 入れ替え型（G）、破壊再構築（L）

複数を組み合わせるのが普通。たとえば「ランダム貪欲 + Look-ahead + 過去改変」のような組み合わせも自然。

### 1.7 派生を横断する2つの軸

| 軸 | 値 | 該当する派生 |
|------|------|------|
| 過去の扱い | 触らない | A, B, D, E, H, I, J |
| 過去の扱い | 編集する | F, G |
| 過去の扱い | 後悔として測る | C, K |
| 未来の見方 | 見ない | A, B, F, G, J |
| 未来の見方 | 後悔（最善と次善の差） | C, K |
| 未来の見方 | k 手先まで | D |
| 未来の見方 | 最後まで | E |

新しい派生を考えるとき、この2軸で空白マスを見つけると新規性が出る。

## 第2部：評価関数の設計原則

評価関数 `f(s)` は、貪欲・焼きなまし全てを動かす中核。問題が同じでも、評価関数の出来次第でスコアが大きく変わる。

### 2.1 評価関数の役割

評価関数が担う役割は次の3つ：

1. **方向性の提示**：探索を最終目標に向かわせる
2. **タイブレーク**：同じくらい良い候補の中で優劣をつける
3. **整合性の維持**：制約違反を防ぐ、または許容範囲に抑える

### 2.2 設計の基本原則

#### 原則1：最終スコアに沿わせる

最終スコア関数そのものを評価関数にできるなら、それが最も素直。ただし、

- 最終スコアが「全て終わってからしか測れない」場合は、途中で測れる代理指標を作る
- 最終スコアが離散的すぎる場合は、滑らかな代理を作る

#### 原則2：将来予測項を加える

現在状態の良さだけでなく、「ここから先で得られそうなスコアの推定」を加える。

- 残り目的地までの最短距離下界
- 残り資源で達成可能なスコア上限
- 残り時間で実行可能な操作数

この項があるかどうかで、貪欲の質が大きく変わる。

#### 原則3：ペナルティ項で制約を表現

制約違反に大きなマイナスを与える。

- ハードペナルティ：違反したら絶対選ばれないほど大きな値
- ソフトペナルティ：違反度に応じた連続的なマイナス
- 整合性緩和：完全な実行可能性を求めず、ペナルティで緩く扱う

焼きなましでは、ペナルティの重みを徐々に上げる戦略（progressive penalization）も有効。

#### 原則4：複数指標を辞書式で扱う

主目的と副目的があるとき、

- **線形和**：`α × main + β × sub`、最も素直だが重みの調整が必要
- **辞書式**：主目的の差が閾値以上なら主目的で比較、未満なら副目的で比較
- **多目的を保持**：Pareto front を保持して、後段で選ぶ

通常は線形和で十分。スコアの単位が大きく違う場合や、副目的が完全にタイブレーク用の場合は辞書式が向く。

#### 原則5：差分計算可能な形にする

評価関数の絶対値を毎回計算すると遅い。差分計算できる形に設計する：

- 状態変化の「影響範囲」が局所的になるよう、評価項を分解する
- 各評価項を独立に持ち、変化した項のみ再計算
- 焼きなましでは差分計算が必須

#### 原則6：滑らかさを確保する

評価値の段差が大きいと、貪欲・焼きなましともに迷う：

- 「あと一歩で達成」と「達成済み」の差を大きくしない
- 距離・コストは段階的に減少するよう設計
- バイナリな成否ではなく、進捗度として測る

#### 原則7：時間スケールに応じて変える

問題の時間軸が長い場合、評価関数を時間と共に変える：

- 序盤：探索を広げる、多様性重視
- 終盤：絞り込む、最終スコア重視
- 焼きなましの温度スケジュールと同様の発想

### 2.3 設計パターン

#### パターンA：単純スコア + 残り見込み

```
f(s) = (現在のスコア) + (残りで得られるスコアの楽観的上限)
```

A* と同じ発想。残り見込みが楽観的なら、最終スコアの上界として機能する。

#### パターンB：主目的 + タイブレーク

```
f(s) = main(s) + ε × sub(s)
```

ε は十分小さい正の数。`main` が同じ候補同士で `sub` が効く。

#### パターンC：制約緩和 + ペナルティ

```
f(s) = scoring(s) - λ × violation(s)
```

`violation` は制約違反度。`λ` を大きくするとハード制約、小さくするとソフト制約。

#### パターンD：多項目線形和

```
f(s) = w_1 × term_1(s) + w_2 × term_2(s) + ... + w_n × term_n(s)
```

各項が異なる側面を測る。重み `w_i` はパラメータチューニングで決める。

#### パターンE：シミュレーション評価

```
f(s) = simulate(s).final_score
```

候補ごとに先を仮想実行して評価。Roll-out 貪欲・MCTS 系。

### 2.4 評価関数のデバッグ・チューニング

#### 観点1：評価値の分布を見る

候補のスコアが「全部同じ」「極端な値が混ざる」場合、評価関数が機能していない兆候。

- 全部同じ：タイブレーク項が足りない
- 極端な値が混ざる：スケールが揃っていない、ペナルティが強すぎる

#### 観点2：1ステップごとの選択が妥当か

各ステップで何が選ばれたか、なぜそれが選ばれたか（各項のスコアの内訳）をログに出す。意図しない選択が頻発するなら、項の重みを見直す。

#### 観点3：項を1つずつ外して効果を見る

`w_i = 0` にして実行し、スコアが下がるかを確認。下がらない項は無駄、上がる項は逆効果。

#### 観点4：パラメータの感度

重みを 0.5x, 1x, 2x で振って、スコアの変化を見る。極端に感度が高いパラメータは慎重に、感度が低いパラメータは固定でよい。

### 2.5 よくある落とし穴

- **最終スコアと評価関数の乖離**：途中で良い評価でも最終スコアが伸びない。代理指標と最終指標の関係を確認する
- **ペナルティが強すぎる**：探索が制約遵守に偏り、本来の最適化が進まない
- **ペナルティが弱すぎる**：制約違反を改善しないまま終わる
- **重みの過剰チューニング**：特定のテストケースに過適合する。複数ケースで検証する
- **計算コストの肥大**：評価関数が重すぎて反復回数が稼げない。差分計算で軽量化する
- **滑らかさの欠如**：評価値が段差状で、貪欲・焼きなましが進まない

## 第3部：貪欲派生と評価関数の組み合わせ

派生と評価関数は独立した軸ではなく、相互に影響する。代表的な組み合わせを整理する。

| 派生 | 相性の良い評価関数の設計 |
|------|------|
| 通常貪欲（A） | 現在の利得最大化、シンプルな線形和 |
| 後悔ベース（C, K） | 最善と次善の差を組み込む |
| Look-ahead（D） | k 手先の状態を評価できる形 |
| Roll-out（E） | 最終スコアそのもの |
| 過去改変（F） | 整合性ペナルティ + 改変コスト |
| 制約伝播（H） | 自由度・残選択肢数を項に入れる |
| 多段階（I） | 段階ごとに異なる評価関数 |

派生を変えると、最適な評価関数も変わる。派生を決めてから評価関数を設計し、評価関数を変えたら派生も再検討する、という往復が現実的。

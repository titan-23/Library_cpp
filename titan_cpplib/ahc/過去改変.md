# 過去改変貪欲 指南書

AHC 等のヒューリスティック問題で有効な「過去改変貪欲」について、考え方・適用判断・設計方針・高速化方針をまとめる。自分の見直し用、および AI に渡す参照ドキュメント用。

---

## 1. 過去改変貪欲とは

解を逐次的に構築していく貪欲法の一種で、**現在の操作をうまく実行するために、過去の操作列を遡って書き換える** ことを許す。書き換え後の過去が、それ以降の操作列と矛盾なく実行可能であることを保証する範囲で行う。

### 1.1 手続き

貪欲の各ステップ t で、次を1つ選んで確定する：

- 現在ターンに実行する操作 `current_action`
- それと組で行う、過去への編集の集合 `past_mods`（0個以上の挿入/置換/削除）

`past_mods` を適用した後の操作列は、元の操作列と同じ現在状態に到達できるよう、整合性チェックを通したものでなければならない。確定後、貪欲は次のステップに進む。**過去への編集も「現在のステップで行う決定」の一部** であり、確定したら戻らない。

### 1.2 似て非なるものとの区別

- **バックトラック**：探索が行き詰まったら過去の分岐を **戻って** 別の選択を試す。過去改変貪欲は戻らない（貪欲）。過去への編集は「元の決定をやり直す」のではなく「元の決定列に整合性を保ったまま編集を加える」
- **完成後の局所探索（焼きなまし等）**：完成した解に対する近傍操作。過去改変貪欲は **構築中** に編集を行う。「現在のステップを進めるために、過去を編集する」という動機を持つ
- **挿入法（Cheapest Insertion 等）**：新要素を最適な位置に挿入する。過去の **決定の中身そのもの** は変えない。過去改変貪欲は決定の中身に挿入/置換/削除を加える

「今やりたい操作」がトリガーになり、「過去のあの時点でこの操作を挟んでおけば、今が楽になる」という反実仮想を、整合性チェックを経て実際の操作列に取り込むのが過去改変貪欲。

## 2. 本質：時間的リソースの再配分

過去改変貪欲の核心は、**時間的に分散した操作リソースを再配分する** こと。

通常の貪欲は「現時点で払うコスト」を最小化するが、過去改変貪欲は「過去のターンに作業を寄せて、現在のターンを軽くする」という再配分を行う。総コストは変わらない（または若干増える）が、**作業の時間配置を最適化する** ことで、結果的に総ターン数が減る。

特に、現在の操作が極端に重い状況で、過去のスカスカなターンに作業を1つ寄せるだけで現在が大幅に軽くなる **時間的非対称性** を利用する。

## 3. 適用判断

新問題に対して、過去改変貪欲が向くかを以下で判断する。

### 3.1 必要条件

- **状態に蓄積構造がある**：盤面への配置・資源・記録など、過去の操作の結果が積み上がる場所がある
- **操作の依存関係が疎**：過去に1操作を挟み込んでも、その後の操作列の大部分がそのまま実行可能
- **「現在の困難」と「過去の余裕」のミスマッチ**：過去にちょっと準備しておけば現在が楽になる構造

### 3.2 強く効く条件

- **過去改変の追加コストが小さく、効果が大きい**（レバレッジが効く）
- **操作1個の効果が大きい**（蓄積される1要素が後続に大きく影響する）

### 3.3 可換性の階層

操作の可換性の度合いが、過去改変貪欲の実装難易度を直接決める。

- **レベル0：完全可換**。順序が結果に一切影響しない。操作列は「各操作タイプの累積量」に還元され、時間軸自体が消える。過去改変が最も強力に効く
- **レベル1：グループ内可換、グループ間独立**。整合性チェックがグループごとに分解できる
- **レベル2：グループ内可換、グループ間は共有資源で依存**。共有資源の状態履歴を意識する必要があるが、依存範囲は局所的
- **レベル3：順序依存性が強い**。可換な部分集合がほとんど取れない。過去改変貪欲が成立しにくいか、整合性チェックが極めて重くなる

レベル0〜2なら過去改変貪欲が有効。レベル3なら別手法を検討する。

## 4. 過去改変のパターン分類

新問題に対しては、まずどのパターンが当てはまるかを考える。

- **仕込み型**：過去に「準備操作」を差し込み、現在の状態に必要な要素を追加する。「今 X が欲しい → 過去に X を準備する操作を挿入」。最も典型的かつ強力
- **寄り道型**：過去の経路を、目的地を経由するように書き換える。「次に P に行きたい → 過去の経路を P に寄る経路に置換」。順序固定の巡回問題で有効
- **交換型**：過去の操作の中身を別のものに差し替える。「今 X が必要 → 過去の Y 取得を X 取得に置換」。資源獲得系で有効
- **前倒し型**：未来でやる予定の操作を過去に前倒しする。定期的・必須の操作がある問題で有効
- **累積量再配分型**：操作が完全可換（レベル0）な場合の極限形。操作列を累積量ベクトルに還元し、その成分を最適化する。時間軸の概念が消える

### 4.1 型の横断的整理

各型を「何を改変するか」「典型的に効く問題構造」で並べると：

| 型             | 改変対象       | 典型的に効く問題構造                       |
| -------------- | -------------- | ------------------------------------------ |
| 仕込み型       | 過去に1個追加  | 状態に蓄積構造あり、現在に「前提条件」が欲しい |
| 寄り道型       | 過去の区間を別の区間に置換 | 順序固定の巡回、過去の経路が現在の目的地近くを通る |
| 交換型         | 過去の1要素を別の1要素に置換 | 資源獲得・割り当て、現在必要なものを過去に取り損ねた |
| 前倒し型       | 未来の予定を過去に移動 | 必ずやる操作・周期的作業がある              |
| 累積量再配分型 | 操作タイプの累積量を変更 | 操作が完全可換、時間軸を消せる              |

### 4.2 型の選び方

新問題に対しては、次の順で判定する：

1. 可換性レベル（§3.3）を判定 → レベル0なら **累積量再配分型** が第一候補
2. 「何を達成したいか」が単発の準備で済むなら **仕込み型**
3. 経路・順序の最適化が中心なら **寄り道型**
4. 過去取得・過去割当の差し替えなら **交換型**
5. 周期作業・前倒し可能な確定操作があれば **前倒し型** を併用

複数型が混在することはよくある。優先される型を主軸に設計し、他は補助的に使う。

## 5. 設計フロー

### 5.1 解の表現を定める

- **Action**：最終出力の1単位（1ターン分の操作）
- **State**：構築中に保持する状態。現在位置・進捗・盤面の蓄積量に加え、整合性判定に必要な要約情報を持つ

### 5.2 過去改変の単位を定める

**Modification** の種類（挿入 / 置換 / 削除）とデータ（対象ターン、新しい Action）を決める。

**改変の粒度**を、微小（1手単位）かマクロ（複数手の塊）から選ぶ。

- 微小単位：柔軟だが、意味の薄い候補が多く、候補数が爆発しやすい
- マクロ単位：意味のある単位（「鬼1個を端まで押し出す」「コンベアを k 回連続で回す」）でまとめる。候補数が絞られ、各候補が現在状態に意味ある変化を与える。整合性チェックも一括

可換性が高い（§3.3 レベル0〜1）ほどマクロ化の恩恵が大きい。マクロの粒度は「現在状態に意味のある変化を与える最小単位」「整合性チェックが完結する単位」を目安に決める。

**整合性条件**を明示する：

- 対象ターンに、その操作が実行可能
- 改変後の過去操作列が、現在状態に到達可能
- 改変によって、過去・未来の他の操作が壊れない

### 5.3 探索アルゴリズムを選ぶ

過去改変貪欲は **思考のフレームワーク** であり、探索手法から独立した概念。問題の構造に応じて、

- 純粋貪欲：各ステップで現在最善の遷移を1つ選び確定
- ダイクストラ / A*：コスト最小化が明確で、状態空間が同一視可能な場合
- BFS：コストが一様の場合

を選ぶ。ビームサーチや焼きなましと組み合わせる場合はそれぞれのライブラリ側で。

### 5.4 整合性チェックの方針を決める

- **方針X**：整合性に必要な情報を State に畳み込み、State 内で完結。最もきれい
- **方針Y**：過去操作列を別管理し、過去改変ごとに参照して判定。判定コストが高いが State 設計の自由度が高い

## 6. 型と責務

```cpp
// 最終出力の1ターン分
struct Action { ... };

// 過去改変1単位（粒度は問題により1手単位 or マクロ単位）
struct Modification {
    enum class Kind { INSERT, REPLACE, ERASE };
    Kind kind;
    int turn;
    Action action;   // INSERT, REPLACE のとき有効
};

// 貪欲の1ステップ：現在操作 + 過去改変リスト
struct Transition {
    Action current_action;
    std::vector<Modification> past_mods;
    ScoreType cost;
};

class State {
public:
    void init();
    bool is_goal() const;

    // 現状態から到達可能な遷移を列挙（通常遷移 + 過去改変付き遷移）
    void get_transitions(std::vector<Transition> &out, const History &history) const;

    // 整合性チェック
    bool is_consistent(const Modification &mod, const History &history) const;

    void apply(const Transition &t);
};

// 過去の操作列（貪欲なので State も History も1本ずつ）
class History {
public:
    int size() const;
    const Action& at(int turn) const;
    void append(const Action &a);
    void apply_modification(const Modification &m);
    std::vector<Action> finalize() const;
};
```

State は「現在状態 + 整合性判定に必要な要約」、History は「過去操作列そのもの」と責務を分離する。

整合性チェックを高速化するインデックス構造（問題依存）は State の一部として持ち、`append` / `apply_modification` と連動して差分更新する。

## 7. 高速化方針

### 7.1 整合性チェックの高速化（最重要）

- **差分管理**：整合性判定に必要な情報を、append・改変ごとに O(1) または O(log) で差分更新
- **二段階チェック**：軽い判定で明らかな NG を弾き、survivors のみ厳密判定
- **キャッシュ**：同じ (現状態, 改変候補) に対する判定結果を memo

### 7.2 候補列挙の高速化

- **候補の構造化**：全候補を素朴に列挙せず、「最善候補」を構成的に求める
- **対象の限定**：改変候補を「現在の操作にとって本当に有効なもの」に絞る

### 7.3 履歴管理

整合性判定に必要な要約だけを State に持たせ、append・改変のたびにインクリメンタルに更新する。

---

## 8. よくある落とし穴

- **整合性チェックの漏れ**：改変によって過去・未来の操作が壊れるケースを見落とす。整合性条件を最初に列挙してテストする
- **コスト計算の見落とし**：過去改変は「挿入1ターン」に見えても、整合性を保つために連鎖的な追加改変が必要なことがある。コストは連鎖を含めて計算する
- **候補列挙の網羅性不足**：対象を狭く絞ると本来有効な改変を見落とす。原則として全候補を列挙し、絞るのは軽量判定で有効性が低いと分かってから
- **状態と履歴の責務混在**：State は「現在状態 + 要約」、History は「過去操作列そのもの」と明確に分離する

## 9. 一段抽象化された理解

過去改変貪欲は本質的に、

**「解空間を、各時点の決定の列ではなく、決定列全体に対する編集列として捉え直す」**

ことをしている。通常の貪欲は「時刻 t に何をするか」を順に決めるが、過去改変貪欲は「これまでの決定列全体に対して、どんな編集を加えるか」を時刻 t ごとに決める。許される編集は append だけでなく insert / replace / erase を含む。

### 極限形：時間軸が消える

操作が完全可換（§3.3 レベル0）な場合、操作列は「各操作タイプの累積量」のベクトルとして表現でき、「過去のターン t に何を挿入するか」という時間軸付きの問いは消える。過去改変貪欲の極限は **時間軸のない累積量最適化** である。

完全可換でなくても、可換な部分集合についてはこの還元が部分的に成立する。問題を見るときには、

- どこまで時間軸を消せるか
- 時間軸を残さざるを得ない部分はどこか

を最初に切り分けると、設計が大きく単純化できる。

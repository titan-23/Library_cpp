# 過去改変貪欲の手引き

AHC 等のヒューリスティック問題で有効な「過去改変貪欲」について、考え方、適用の判断、設計方針、高速化の方針をまとめます。自分で見直すときと AI に参照ドキュメントとして渡すときに使用します。

---

## 1. 過去改変貪欲の定義

解を逐次的に構築していく貪欲法の一種で、**現在の操作を実行しやすくするために、過去の操作列を遡って変更する** ことを許容します。変更は、変更後の過去の操作列がそれ以降の操作列と矛盾なく実行可能であることを保証できる範囲で行います。

### 1.1 手続き

貪欲法の各ステップ t では、次の組を 1 つ選んで確定します。

- 現在のターンに実行する操作 `current_action`
- この操作と組にして行う、過去の操作列への編集の集合 `past_mods` (0 個以上の挿入、置換、削除)

`past_mods` を適用した後の操作列は、元の操作列と同じ現在状態に到達できるように、整合性チェックを通過している必要があります。確定した後、貪欲法は次のステップに進みます。**過去への編集も「現在のステップで行う決定」の一部** であり、確定した後は元に戻しません。

### 1.2 類似する手法との違い

- **バックトラック**：探索が行き詰まった場合に、過去の分岐点まで **戻って** 別の選択を試します。過去改変貪欲は貪欲法であり、戻りません。過去への編集は、元の決定をやり直すのではなく、整合性を維持したまま元の決定列に編集を加える操作です。
- **完成後の局所探索 (焼きなまし等)**：完成した解に対して近傍操作を行う手法です。過去改変貪欲は解の **構築中** に編集を行います。過去を編集する目的は、現在のステップを進めることです。
- **挿入法 (Cheapest Insertion 等)**：新しい要素を最適な位置に挿入します。過去の **決定の内容そのもの** は変更しません。過去改変貪欲は決定の内容に挿入、置換、削除を加えます。

過去改変貪欲では、現在実行したい操作がきっかけになります。「過去のある時点でこの操作を挿入しておけば、現在の操作が容易になる」という反実仮想を、整合性チェックを経て実際の操作列に取り込みます。

## 2. 本質：時間的リソースの再配分

過去改変貪欲の核心は、**時間的に分散した操作リソースを再配分する** ことです。

通常の貪欲法は現時点で払うコストを最小化しますが、過去改変貪欲は過去のターンに作業を移して、現在のターンの作業を減らすように再配分します。総コストは変化しないか若干増えますが、**作業の時間配置を最適化する** ことで、結果として総ターン数が減ります。

特に、現在の操作の負担が極端に大きい状況では、作業の少ない過去のターンに作業を 1 つ移すだけで現在の負担が大幅に小さくなります。過去改変貪欲はこの **時間的非対称性** を利用します。

## 3. 適用判断

新しい問題に過去改変貪欲が適しているかは、次の条件で判断します。

### 3.1 必要条件

- **状態に蓄積構造がある**：盤面への配置、資源、記録など、過去の操作の結果が蓄積される場所があります。
- **操作の依存関係が疎**：過去に 1 つの操作を挿入しても、その後の操作列の大部分をそのまま実行できます。
- **「現在の困難」と「過去の余裕」のミスマッチ**：過去に少し準備しておけば、現在の操作が容易になる構造があります。

### 3.2 効果が大きくなる条件

- **過去改変の追加コストが小さく、効果が大きい**
- **操作 1 個の効果が大きい**：蓄積される 1 つの要素が後続の操作に大きく影響します。

### 3.3 可換性の階層

過去改変貪欲の実装の難易度は、操作の可換性の度合いで直接定まります。

- **レベル 0：完全可換**。操作の順序は結果に一切影響しません。操作列は「各操作タイプの累積量」に還元され、時間軸自体を考慮する必要がなくなります。過去改変の効果が最も大きくなります。
- **レベル 1：グループ内可換、グループ間独立**。整合性チェックをグループごとに分解できます。
- **レベル 2：グループ内可換、グループ間は共有資源で依存**。共有資源の状態の履歴を考慮する必要がありますが、依存する範囲は局所的です。
- **レベル 3：順序依存性が強い**。可換な部分集合がほとんど存在しません。過去改変貪欲が成立しにくいか、整合性チェックのコストが極めて大きくなります。

レベル 0〜2 では過去改変貪欲が有効です。レベル 3 では別の手法を検討します。

## 4. 過去改変のパターン分類

新しい問題では、まずどのパターンが当てはまるかを検討します。

- **仕込み型**：過去に準備の操作を挿入し、現在の状態に必要な要素を追加します。例えば、現在 X が必要な場合に、過去に X を準備する操作を挿入します。最も典型的で強力な型です。
- **寄り道型**：過去の経路を、目的地を経由するように変更します。例えば、次に P へ移動したい場合に、過去の経路を、P を経由する経路に置換します。順序が固定された巡回問題で有効です。
- **交換型**：過去の操作の内容を別の内容に差し替えます。例えば、現在 X が必要な場合に、過去の Y の取得を X の取得に置換します。資源を獲得する問題で有効です。
- **前倒し型**：将来実行する予定の操作を過去に前倒しします。定期的に行う操作や必須の操作がある問題で有効です。
- **累積量再配分型**：操作が完全可換 (レベル 0) な場合の極限形です。操作列を累積量のベクトルに還元し、その成分を最適化します。時間軸を考慮する必要はありません。

### 4.1 型の比較

各型の改変対象と、その型が有効な典型的な問題構造は次のとおりです。

| 型             | 改変対象       | 有効な問題構造の典型例                     |
| -------------- | -------------- | ------------------------------------------ |
| 仕込み型       | 過去に 1 個追加 | 状態に蓄積構造があり、現在の操作に前提条件が必要 |
| 寄り道型       | 過去の区間を別の区間に置換 | 順序が固定された巡回で、過去の経路が現在の目的地の近くを通る |
| 交換型         | 過去の 1 要素を別の 1 要素に置換 | 資源の獲得や割り当てで、現在必要なものを過去に取得し損ねた |
| 前倒し型       | 未来の予定を過去に移動 | 必ず行う操作や周期的な作業がある            |
| 累積量再配分型 | 操作タイプの累積量を変更 | 操作が完全可換で、時間軸を考慮する必要がない |

### 4.2 型の選び方

新しい問題では次の順に判定します。

1. 可換性のレベル (§3.3) を判定し、レベル 0 であれば **累積量再配分型** を第一候補にします。
2. 達成したいことが一度の準備で済む場合は **仕込み型** を選択します。
3. 経路や順序の最適化が中心である場合は **寄り道型** を選択します。
4. 過去の取得や割り当てを差し替える場合は **交換型** を選択します。
5. 周期的な作業や、前倒しできる確定した操作がある場合は **前倒し型** を併用します。

複数の型が混在することはよくあります。優先する型を中心に設計し、他の型は補助的に使用します。

## 5. 設計の手順

### 5.1 解の表現

- **Action**：最終出力の 1 単位で、1 ターン分の操作を表します。
- **State**：構築中に保持する状態です。現在位置、進捗、盤面の蓄積量に加えて、整合性判定に必要な要約情報も含みます。

### 5.2 過去改変の単位

**Modification** の種類 (挿入、置換、削除) とデータ (対象のターン、新しい Action) を定めます。

**改変の粒度** は、1 操作ずつの微小単位と、複数の操作をまとめたマクロ単位から選択します。

- 微小単位：柔軟ですが、意味のある変化をほとんど与えない候補が多く、候補数が急増しやすくなります。
- マクロ単位：「鬼 1 個を端まで押し出す」「コンベアを k 回連続で回す」のような意味のある単位で操作をまとめます。候補数が絞られ、各候補が現在状態に意味のある変化を与えます。整合性チェックも一括で行うことができます。

可換性が高い (§3.3 のレベル 0〜1) ほど、マクロ化の利点が大きくなります。マクロの粒度は、現在状態に意味のある変化を与える最小の単位と、整合性チェックが完結する単位を目安に定めます。

**整合性条件** は、次のように明示します。

- 対象のターンでその操作を実行できること
- 改変後の過去の操作列で現在状態に到達できること
- 改変後も、過去と未来の他の操作を実行できること

### 5.3 探索アルゴリズムの選択

過去改変貪欲は **思考のフレームワーク** であり、探索手法から独立した概念です。探索手法は、問題の構造に応じて次から選択します。

- 純粋貪欲：各ステップで現時点の最善の遷移を 1 つ選んで確定する方法
- ダイクストラ法 / A*：コストの最小化が明確で、状態を同一視できる場合
- BFS：コストが一様な場合

ビームサーチや焼きなましと組み合わせる場合は、それぞれのライブラリで対応します。

### 5.4 整合性チェックの方針

- **方針 X**：整合性の判定に必要な情報を State に含め、State の中で判定を完結させます。最も簡潔な方針です。
- **方針 Y**：過去の操作列を別に管理し、過去改変のたびに参照して判定します。判定のコストは高いですが、State の設計の自由度は高くなります。

## 6. 型と責務

```cpp
// 最終出力の 1 ターン分
struct Action { ... };

// 過去改変の 1 単位 / 粒度は問題に応じて 1 操作単位またはマクロ単位
struct Modification {
    enum class Kind { INSERT, REPLACE, ERASE };
    Kind kind;
    int turn;
    Action action;   // INSERT, REPLACE のとき有効
};

// 貪欲法の 1 ステップ / 現在の操作と過去改変のリスト
struct Transition {
    Action current_action;
    std::vector<Modification> past_mods;
    ScoreType cost;
};

class State {
public:
    void init();
    bool is_goal() const;

    // 現在の状態から到達可能な遷移を列挙する / 通常の遷移と過去改変付きの遷移
    void get_transitions(std::vector<Transition> &out, const History &history) const;

    // 整合性チェック
    bool is_consistent(const Modification &mod, const History &history) const;

    void apply(const Transition &t);
};

// 過去の操作列 / 貪欲法なので State も History も 1 本ずつ
class History {
public:
    int size() const;
    const Action& at(int turn) const;
    void append(const Action &a);
    void apply_modification(const Modification &m);
    std::vector<Action> finalize() const;
};
```

State が現在の状態と整合性判定に必要な要約を、History が過去の操作列そのものを保持するように責務を分離します。

整合性チェックを高速化するインデックス構造は問題に依存します。この構造は State の一部として保持し、`append` / `apply_modification` と連動して差分更新します。

---

## 7. 高速化方針

### 7.1 整合性チェックの高速化 (最重要)

- **差分管理**：整合性判定に必要な情報を、append と改変のたびに O(1) または O(log) で差分更新します。
- **二段階チェック**：軽量な判定で明らかに不適切な候補を除外し、残った候補だけを厳密に判定します。
- **キャッシュ**：同じ (現状態, 改変候補) に対する判定結果をメモ化します。

### 7.2 候補列挙の高速化

- **候補の構造化**：全候補を素朴に列挙せず、最善の候補を構成的に求めます。
- **対象の限定**：改変候補を、現在の操作にとって本当に有効なものに絞り込みます。

### 7.3 履歴管理

整合性判定に必要な要約だけを State に保持させ、append と改変のたびにインクリメンタルに更新します。

## 8. よくある誤り

- **整合性チェックの漏れ**：改変によって過去や未来の操作が実行できなくなる場合を検出できないことがあります。整合性条件は最初に列挙し、テストで確認するようにします。
- **コスト計算の漏れ**：過去改変は 1 ターンの挿入に見えても、整合性を維持するために連鎖的な追加の改変が必要な場合があります。コストは連鎖を含めて計算するようにします。
- **候補列挙の網羅性不足**：対象を狭く絞ると、本来有効な改変が候補から漏れる場合があります。原則として全候補を列挙し、候補を絞るのは軽量な判定で有効性が低いことを確認してからにします。
- **状態と履歴の責務の混在**：State は現在の状態と要約、History は過去の操作列そのものを保持するように、責務を明確に分離します。

## 9. 抽象化した捉え方

過去改変貪欲は本質的に、**解空間を、各時点の決定の列ではなく、決定列全体に対する編集の列として捉え直す** 手法です。通常の貪欲法は時刻 t に何をするかを順に決定しますが、過去改変貪欲は、これまでの決定列全体にどのような編集を加えるかを時刻 t ごとに決定します。許容する編集は append だけでなく、insert / replace / erase も含みます。

### 極限形：時間軸のない累積量最適化

操作が完全可換 (§3.3 のレベル 0) な場合、操作列は各操作タイプの累積量のベクトルとして表現できます。このとき、過去のターン t に何を挿入するかという時間軸に依存する問いを考える必要はなくなります。過去改変貪欲の極限は **時間軸のない累積量最適化** です。

完全可換でない場合も、可換な部分集合についてはこの還元が部分的に成立します。問題を検討するときは、最初に次の部分を切り分けると、設計を大幅に単純化できます。

- 時間軸を考慮せずに済む部分
- 時間軸を考慮する必要がある部分

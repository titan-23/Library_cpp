# OnlineDynamicConnectivity

無向グラフに対して辺の追加と削除を行いながら、連結判定、連結成分の大きさ、連結成分数を求めます。操作はオンラインで処理し、近似や確率的な連結判定は行いません。多重辺は辺 ID で区別します。

Holm–de Lichtenberg–Thorup (HDT) 法を、レベルごとの Euler tour tree と splay 木で実装しています。HDT 法の詳細は[原論文](https://www.cs.princeton.edu/courses/archive/fall07/cos521/handouts/poly.pdf)を参照してください。

## 使用方法

```cpp
#include "titan_cpplib/graph/online_dynamic_connectivity.cpp"

// 第 2 引数で初期辺と今後の追加を含めた累計の辺 ID 数を予約する
titan23::OnlineDynamicConnectivity dc(500000, 1000000);
int a = dc.add_edge(0, 1);
int b = dc.add_edge(1, 2);
int parallel = dc.add_edge(0, 1);

bool connected = dc.same(0, 2); // true
int vertices = dc.size(0);      // 3
dc.erase_edge(a);              // 多重辺が残るため、連結のまま
dc.erase_edge(parallel);
connected = dc.same(0, 2);     // false
vertices = dc.size(0);         // 1
```

頂点番号は `0 <= v < n` の範囲で指定します。辺 ID は 0 から順に発行され、削除しても再利用されません。初期辺を `add_edge` で登録した後は、そのまま更新と問い合わせを続けることができます。

## 初期構築と最初の削除

初期状態では Union-Find で連結成分を管理します。動的木は、最初に木の辺を削除するときに一括で構築します。辺を 1 本ずつ動的木に挿入する代わりに、各木を走査して Euler tour を作成し、その列から平衡な木を構築します。累計の発行 ID 数を `I` とすると、初回のコストは `O(n+I)` です。

このコストを削除処理に含めたくない場合は、初期辺の登録後に動的木を明示的に構築することができます。

```cpp
// 初期辺を add_edge で登録した後、更新のループに入る前に呼び出す
dc.prepare_dynamic();
```

この呼び出しは任意であり、複数回呼び出しても構築は一度だけ行われます。空グラフの段階で呼び出すこともできます。準備前の自己ループと非木辺の削除には、一括構築は必要ありません。

オブジェクトの構築直後、初期辺を登録する前に `prepare_dynamic()` を呼び出すと、以後の辺は従来と同様に 1 本ずつ動的木に挿入されます。この方法では、一括構築した場合と木の形や巡回順が異なり、構築後の更新時間やピークメモリにも差が生じます。初期構築の時間が支配的でない用途では、この方法も比較の候補になります。

Union-Find の連結成分キャッシュは、実際に成分が分断されるまで使用します。木の辺を削除しても、代替辺で再接続できた場合はキャッシュが有効なままです。分断が発生した時点でキャッシュを無効化し、以後の判定には動的木を使用します。その後に再接続しても、キャッシュは再構築しません。

## API と計算量

| API | 内容 | 時間 |
|---|---|---|
| `OnlineDynamicConnectivity(n)` | 頂点数 `n`、辺なしで構築 | `O(n)` |
| `OnlineDynamicConnectivity(n, cap)` | 上記に加えて累計 `cap` 本分を予約 | `O(n)`、予約する容量に依存する確保を含む |
| `prepare_dynamic()` | 動的木を一括構築 | 初回 `O(n+I)`、以後 `O(1)` |
| `add_edge(u, v)` | 辺を追加し、新しい ID を返す | 準備前は償却 `O(α(n))`、準備後は償却 `O(log n)` |
| `erase_edge(id)` | 有効な辺を削除して `true`、削除済みまたは範囲外なら `false` | 更新列全体で償却 `O(log² n)`、初期化のコストは別に計上 (下記の累計の評価を参照) |
| `same(u, v)` | 連結であるか | 成分キャッシュ有効時は償却 `O(α(n))`、以後は償却 `O(log n)` |
| `size(v)` | `v` の連結成分に含まれる頂点数 | 成分キャッシュ有効時は償却 `O(α(n))`、以後は償却 `O(log n)` |
| `group_count()` | 連結成分数 | `O(1)` |
| `edge_count()` | 現在有効な辺数 | `O(1)` |
| `edge_id_count()` | 削除済みを含む累計の発行 ID 数 | `O(1)` |
| `edge_active(id)` | 有効な辺 ID であるか | `O(1)` |
| `reserve_edges(cap)` | 累計 ID 数と各階層の辺の領域を予約 | 再確保やコピーをする領域に依存 |

`α(n)` は Union-Find の計算量に現れる逆 Ackermann 関数です。表に示した探索の計算量とは別に、初めて使用する階層の頂点配列と隣接リストの先頭の初期化には `O(n)` かかります。作成する階層数を `L` とすると、その累計は `O(nL)` です。`prepare_dynamic()` が準備するのは最下層だけであり、後で使用する全階層を事前に確保するわけではありません。

全頂点が連結済みの場合や全頂点が孤立している場合などは、`same` と `size` が定数時間で結果を返します。ただし、これらは一般の入力での計算量とは区別して扱います。

自己ループは有効な辺に含めますが、連結性には影響しません。多重辺はそれぞれ別の ID であるため、1 本だけ削除しても別の辺が残ります。既定のコンストラクタで頂点数 0 のオブジェクトを構築することもできますが、存在しない頂点を渡す操作はできません。

## 償却計算量の根拠と評価範囲

計算量は、各操作 1 回の最悪時間ではなく、操作列全体での償却時間として評価します。元の HDT 法の計算量も更新列に対する償却での保証であり、更新列には初期辺の追加も含まれます ([HDT 原論文](https://u.cs.biu.ac.il/~rodittl/p723-holm.pdf))。

本実装で追加した処理は、次の理由によりこの評価を悪化させません。

- **Union-Find**: サイズによる併合と path splitting を使用しており、償却 `O(α(n))` です。実際に分断が発生した後はフラグを無効化するだけで、削除のたびに全頂点を走査して再構築することはありません。
- **一括構築**: 発行済み ID の走査は `O(I)` です。森の辺数は高々 `n-1` であるため、Euler tour の列挙と平衡な木の構築は `O(n)` です。合計 `O(n+I)` のコストが一度だけかかります。
- **印の更新での splay の省略**: 直接更新するのは最大 4 ノードであり、`O(1)` です。木の形と構造上の部分木サイズを変更しないため、通常の splay のポテンシャル `Φ = Σ log(subtree_size)` も変化しません。4 ノードを超える場合は、その先の祖先を通常どおり splay するため償却 `O(log n)` です。splay を省いて無制限に親をたどる方式ではありません。解析の根拠は [splay の Access Lemma](https://www.cs.cmu.edu/~sleator/papers/self-adjusting.pdf) です。
- **再接続**: 非木辺を昇格させる前に、必要な木の辺を昇格させ、階層ごとの成分サイズの上限を維持します。各辺のレベルは下がらず、1 本の辺が生存期間中に昇格する回数は高々 `O(log n)` 回です。昇格前に試す候補も各階層で 1 本に制限しています。

初期辺の追加も含めた累計の発行 ID 数を `I`、削除の呼び出し数を `D`、`same` と `size` の呼び出し数を `R`、作成した階層数と 1 のうち大きい方を `L` とします。`n >= 2` のとき、初期化も含めた保守的な累計の上界は次のとおりです。

```text
O(nL + (I + D) log² n + R log n),  L <= floor(log₂ n) + 1
```

これは通常の追加、削除、問い合わせの列についての評価であり、`reserve_edges` を明示的に繰り返し呼び出すコストやオブジェクト全体をコピーするコストは別に計上します。固定幅整数の演算は定数時間とし、動的配列の自動拡張は償却で評価します。

`add_edge` 自身の直接の処理は償却 `O(log n)` ですが、全体の計算量を単純な合計の `O(I log n + D log² n)` とはしません。後の削除時に行う辺の昇格も、初期辺を含む各辺の生存期間について計上するためです。一括構築を線形時間で行っても、その後の削除に対するこのコストがなくなるわけではありません。

したがって、初回の木の辺の削除には一括構築のコストが、初めて使用する階層には頂点配列の初期化のコストが加わります。また、splay 自体も償却での保証であるため、準備後でも単一操作の最悪時間が `O(log² n)` であることは保証されません。

## 50 万規模で使用する場合

`N=500000`、初期辺数 `M=500000`、操作数 `Q=500000` での測定結果は[追加改善の性能比較](online_dynamic_connectivity_benchmark_2026-11-12_round2.md)に記載しています。[最初の改善の比較](online_dynamic_connectivity_benchmark_2026-11-12.md)も保存しています。`Q` は追加、削除、問い合わせを合計した数であり、それぞれが 50 万回ではありません。

初期辺が `M` 本、その後の追加回数が `A` 回であれば、予約数の目安は `M+A` です。追加回数が不明な場合は `M+Q` が上限になります。予約は任意であり、容量を超えた場合は自動的に拡張します。後から `reserve_edges` を呼び出す際は、発行済み ID 数以上を指定します。

メモリ量は、累計の発行 ID 数を `I` とすると `O(I+n log n)` です。削除済み ID の記録も保持するため、現在の辺数だけではメモリ量を見積もることができません。階層は必要になった時点で作成し、作成済みの階層は削除後も解放しません。木の辺用のノードは階層内で再利用します。

動的木を構築するまでのメモリ量は `O(I+n)` です。成分キャッシュと一括構築時の作業領域にも `O(n)` を使用します。これらの追加や動的木の形の違いにより、前回版よりピークメモリが増える入力もあります。

実行時間とメモリ量は、木の辺を削除する回数、代わりの辺を少ない探索で発見できるか、到達する階層数などに依存します。測定結果は一般の入力に対する上限ではありません。

## 2026-11-12 の高速化

既存の API と返り値の意味を維持したまま、主に削除後の再接続処理を変更しました。

1. 切り離した小さい側に、その階層の非木辺の候補がなければ、その階層をスキップします。内部辺の昇格を行わないため、木の辺を先に昇格させる必要もありません。
2. 候補がある場合は、まず 1 本だけ調べます。その辺が切断した両側を結ぶ辺であれば、木の辺を昇格させずに再接続します。
3. その 1 本が内部辺であれば、従来どおり木の辺を昇格させてから、非木辺の探索と昇格を行います。試行を 1 本に制限しているため、追加の処理は各階層で償却 `O(log n)` に収まります。
4. 孤立した頂点を含む連結判定では、もう一方の大きい木を splay せずに結果を返します。

切断によって成分の大きさは増えず、昇格を見送った階層も成分サイズの上限を満たし続けます。後で内部の非木辺を上位の階層に移す場合は、その前に必要な木の辺を昇格させます。先行して試す 1 本も、辺の両端の連結性を調べてから採用するため、判定結果の正確さは損なわれません。

追加改善では、上記に加えて初期状態の Union-Find、一括構築、分断まで有効な成分キャッシュを導入しました。切断の直後に求まっている小さい側の木の根も、再接続処理に渡して再利用します。

候補辺の有無を示す印の更新では、祖先の集約値が変化しなくなった時点で伝播を停止します。直接たどるノードは最大 4 個に制限し、それより上の更新は splay で行います。深い木でも、無制限に親をたどり続けることはありません。

## 入力範囲

- `n` と予約数には非負の値を指定します。公開 API には有効範囲内の頂点番号を渡します。
- ノードのサイズを 24 ビットで格納しているため、`3n-2 <= 2²⁴-1`、すなわち `n <= 5,592,405` である必要があります。
- 非木辺の端点を `2*id+side` で表すため、累計の発行 ID 数は `2³⁰` 以下である必要があります。
- 上記の範囲は競技用の入力条件であり、API がすべての条件を例外で確認するわけではありません。
- `same` と `size` も内部の splay 木を変更します。同じオブジェクトに複数のスレッドから同時にアクセスしないでください。

連結性を変化させる辺の追加や削除を行っても、オブジェクトの再構築や前計算の再実行は必要ありません。

# OnlineDynamicConnectivity

無向グラフへ辺を追加・削除しながら、連結判定、連結成分の大きさ、連結成分数を求める。操作はオンラインで処理し、近似や確率的な連結判定は行わない。辺IDで多重辺を区別する。

Holm–de Lichtenberg–Thorup（HDT）法を、レベルごとのEuler tour treeとsplay木で実装している。[原論文](https://www.cs.princeton.edu/courses/archive/fall07/cos521/handouts/poly.pdf)

## 使い方

```cpp
#include "titan_cpplib/graph/online_dynamic_connectivity.cpp"

// 第2引数は、初期辺と今後の追加を含めた累計の辺ID数の予約。
titan23::OnlineDynamicConnectivity dc(500000, 1000000);
int a = dc.add_edge(0, 1);
int b = dc.add_edge(1, 2);
int parallel = dc.add_edge(0, 1);

bool connected = dc.same(0, 2); // true
int vertices = dc.size(0);      // 3
dc.erase_edge(a);              // 多重辺が残るので、まだ連結
dc.erase_edge(parallel);
connected = dc.same(0, 2);     // false
vertices = dc.size(0);         // 1
```

頂点は `0 <= v < n`。辺IDは0から順に発行され、削除しても再利用しない。初期辺を `add_edge` で登録した後、そのまま更新・問い合わせを続けられる。

## 初期構築と最初の削除

初期状態ではUnion-Findで連結成分を管理する。動的木は、最初に木の辺を削除するときに一括構築する。辺を1本ずつ動的木へ挿入する代わりに、各木を走査してEuler tourを作り、平衡な木として組み立てる。初回の費用は、累計発行ID数を `I` として `O(n+I)`。

削除処理へこの費用を持ち込みたくない場合は、初期辺の登録後に明示的に準備できる。

```cpp
// 初期辺を add_edge で登録した後、更新ループへ入る前に呼ぶ。
dc.prepare_dynamic();
```

この呼び出しは任意で、複数回呼んでも構築は一度だけ。空グラフの段階で呼んでもよい。準備前の自己ループ・非木辺の削除には、一括構築は不要。

構築直後、初期辺を登録する前に `prepare_dynamic()` を呼ぶと、以後の辺は従来と同様に1本ずつ動的木へ挿入する。一括構築とは木の形や巡回順が異なり、構築後の更新時間やピークメモリにも差が出る。初期構築の時間が支配的でない用途では、この方法も比較できる。

Union-Findの連結成分キャッシュは、実際に成分が分断されるまで使用する。木の辺を削除しても代替辺で再接続できた場合は有効なまま。分断が起きたらキャッシュを無効化し、以後の判定には動的木を使う。その後再接続しても、キャッシュを作り直す処理は行わない。

## APIと計算量

| API | 内容 | 時間 |
|---|---|---|
| `OnlineDynamicConnectivity(n)` | 頂点数 `n`、辺なしで構築 | `O(n)` |
| `OnlineDynamicConnectivity(n, cap)` | 上記に加えて累計 `cap` 本分を予約 | `O(n)`、予約する容量に依存する確保を含む |
| `prepare_dynamic()` | 動的木を一括構築 | 初回 `O(n+I)`、以後 `O(1)` |
| `add_edge(u, v)` | 辺を追加し、新しいIDを返す | 準備前は償却 `O(α(n))`、準備後は償却 `O(log n)` |
| `erase_edge(id)` | 有効な辺を削除して `true`、削除済み・範囲外なら `false` | 更新列全体で償却 `O(log² n)`、初期化費用は別。下記の累計評価を参照 |
| `same(u, v)` | 連結か | 成分キャッシュ有効時は償却 `O(α(n))`、以後は償却 `O(log n)` |
| `size(v)` | `v` の連結成分に含まれる頂点数 | 成分キャッシュ有効時は償却 `O(α(n))`、以後は償却 `O(log n)` |
| `group_count()` | 連結成分数 | `O(1)` |
| `edge_count()` | 現在有効な辺数 | `O(1)` |
| `edge_id_count()` | 削除済みを含む累計の発行ID数 | `O(1)` |
| `edge_active(id)` | 有効な辺IDか | `O(1)` |
| `reserve_edges(cap)` | 累計ID数と各階層の辺領域を予約 | 再確保・コピーする領域に依存 |

`α(n)` はUnion-Findの逆Ackermann関数。表の探索の計算量とは別に、初めて使う階層の頂点配列・隣接リスト先頭の初期化には `O(n)` かかる。作成する階層数を `L` とすると、その累計は `O(nL)`。`prepare_dynamic()` が準備するのは最下層であり、後の全階層を事前確保するAPIではない。

全頂点が連結済みのときの `same` と `size`、全頂点が孤立している場合などには定数時間で返せる。ただし一般の入力での計算量とは区別する。

自己ループは有効な辺として数えるが、連結性には影響しない。多重辺はそれぞれ別IDなので、1本だけ削除しても別の辺が残る。頂点数0の既定構築にも対応するが、存在しない頂点を渡す操作は行えない。

## 償却計算量の根拠と評価範囲

計算量は、各操作1回の最悪時間ではなく、操作列全体での償却時間として評価する。元のHDT法も更新列に対する償却保証であり、初期辺の追加を含む。[HDT原論文](https://u.cs.biu.ac.il/~rodittl/p723-holm.pdf)

追加した処理は、以下の理由でこの評価を悪化させない。

- **Union-Find**: サイズによる併合とpath splittingを使い、償却 `O(α(n))`。実際の分断後はフラグを無効化するだけで、削除のたびに全頂点を走査して作り直すことはない。
- **一括構築**: 発行済みIDの走査が `O(I)`、森の辺数は高々 `n-1` なのでEuler tourの列挙・平衡な木の構築は `O(n)`。合計 `O(n+I)` を一度だけ支払う。
- **印の更新でのsplay省略**: 直接更新するのは最大4ノードで `O(1)`。木の形・構造上の部分木サイズを変えないため、通常のsplayのポテンシャル `Φ = Σ log(subtree_size)` も変わらない。4ノードを超える場合には、その先の祖先を通常どおりsplayするので償却 `O(log n)`。単にsplayを省いて無制限に親をたどる方式ではない。[splayのAccess Lemma](https://www.cs.cmu.edu/~sleator/papers/self-adjusting.pdf)
- **再接続**: 非木辺を上げる前には必要な木の辺を上げ、階層ごとの成分サイズ上限を維持する。各辺のレベルは下がらず、昇格は1辺の生存期間で高々 `O(log n)` 回。昇格前に試す候補も各階層1本に制限する。

累計発行ID数を `I`（初期辺の追加も含む）、削除呼び出し数を `D`、`same`・`size` の呼び出し数を `R`、作成した階層数と1の大きい方を `L` とする。`n >= 2` について、初期化も含めた保守的な累計上界は次のとおり。

```text
O(nL + (I + D) log² n + R log n),  L <= floor(log₂ n) + 1
```

これは通常の追加・削除・問い合わせ列についての評価で、明示的な `reserve_edges` の反復やオブジェクト全体のコピーの費用は別に数える。固定幅整数の演算を定数時間とし、動的配列の自動拡張は償却で評価する。

`add_edge` 自身の直接処理が償却 `O(log n)` であることから、全体を `O(I log n + D log² n)` と単純に足し合わせることはしない。後の削除時に行う辺昇格も、初期辺を含む各辺の生存期間に対して数えるためである。一括構築を線形時間で済ませても、その後の削除に対するこの費用まで消えるわけではない。

したがって、初回の木の辺の削除には一括構築、初めて使う階層には頂点配列の初期化が加わる。またsplay自体も償却保証なので、準備後でも単一操作の最悪時間を `O(log² n)` とする保証ではない。

## 50万規模で使う場合

`N=500000`、初期辺数 `M=500000`、操作数 `Q=500000` の測定は[追加改善の性能比較](online_dynamic_connectivity_benchmark_2026-11-12_round2.md)に記載した。[最初の改善の比較](online_dynamic_connectivity_benchmark_2026-11-12.md)も保存している。`Q` は追加・削除・問い合わせを合計した数であり、それぞれ50万回ではない。

初期辺が `M` 本、その後の追加回数が `A` 回なら、予約の目安は `M+A`。追加回数が分からなければ `M+Q` が上限になる。予約は任意で、容量を超えても自動拡張する。後から `reserve_edges` を呼ぶ際は発行済みID数以上を指定する。

メモリ量は、累計発行ID数を `I` とすると `O(I+n log n)`。削除済みIDの記録は保持するので、現在の辺数だけでは見積もれない。階層は必要時に作り、作成済みの階層は削除後も解放しない。木の辺用ノードは階層内で再利用する。

動的木を構築するまでは `O(I+n)`。成分キャッシュと一括構築時の作業領域にも `O(n)` を使う。これらの追加や動的木の形の違いにより、前回版よりピークメモリが増える入力もある。

時間もメモリも、木の辺をどれだけ削除するか、代わりの辺をすぐ発見できるか、到達する階層数などに依存する。測定結果は一般の入力に対する上限ではない。

## 2026-11-12の高速化

既存APIと返り値の意味を保ち、主に削除後の再接続を変更した。

1. 切り離した小さい側に、その階層の非木辺の候補がなければ、その階層を飛ばす。内部辺の昇格を行わないので、木の辺を先に昇格させる必要もない。
2. 候補がある場合は、まず1本だけ調べる。切断した両側を結ぶ辺なら、木の辺を昇格させずに再接続する。
3. その1本が内部辺なら、従来どおり木の辺を昇格させてから、非木辺の探索・昇格を行う。試行を1本に制限しているので、追加の仕事は各階層で償却 `O(log n)` に収まる。
4. 孤立した頂点を含む連結判定では、もう一方の大きい木をsplayせずに返す。

切断によって成分の大きさは増えず、昇格を見送った階層も成分サイズの上限を満たし続ける。後で内部の非木辺を上位へ移す場合には、その前に必要な木の辺を昇格する。先行する1本の確認も、辺の両端の連結性を調べてから採用するため、判定結果の正確さは変わらない。

追加改善では、上記に加えて初期のUnion-Find、一括構築、分断まで有効な成分キャッシュを導入した。切断直後に分かっている小さい側の木の根も、再接続処理へ渡して再利用する。

候補辺の有無を示す印の更新では、祖先の集約値が変わらなくなった時点で伝播を止める。直接たどるのは最大4ノードに制限し、それより上への更新はsplayへ戻す。深い木でも無制限に親をたどり続ける実装にはしていない。

## 入力範囲

- `n`、予約数は非負。公開APIの頂点番号は有効範囲内を渡す。
- ノードのサイズを24ビットに格納しており、`3n-2 <= 2²⁴-1`、すなわち `n <= 5,592,405` が必要。
- 非木辺の端点を `2*id+side` で表すため、累計発行ID数は `2³⁰` 以下に収める。
- 上記の範囲は競技用の入力条件であり、すべてを例外で検査するAPIではない。
- `same` と `size` も内部のsplay木を変更する。同じオブジェクトへ複数スレッドから同時アクセスしない。

連結性を変える辺の追加・削除には、オブジェクトの作り直しや前計算のやり直しは不要。
